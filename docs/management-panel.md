# پنل مدیریت سرور و نرم‌افزار خانه‌یار

این پنل از برنامه و پنل پشتیبانی مستقل است. رابط React فارسی و راست‌به‌چپ، سرویس FastAPI جدا و پایگاه هویت SQLite خصوصی دارد. توقف API یا دیتابیس خانه‌یار، ورود به مدیریت و مشاهدهٔ سابقهٔ آن را متوقف نمی‌کند.

## دیدن نسخهٔ محلی

روی `start-management.bat` دوبار کلیک کنید یا `npm run management:preview` را بزنید. نشانی پیش‌فرض `http://127.0.0.1:5910` است؛ اگر پورت در ویندوز رزرو شده باشد، راه‌انداز یک پورت آزاد انتخاب و نشانی واقعی را چاپ می‌کند. `management:check` نشانی فعال را بررسی می‌کند.

نام کاربری و رمز تولیدشده در `.local-test/management/access.txt` روی همین رایانه نگه داشته می‌شوند. راه‌اندازی دوباره حساب یا اطلاعات قبلی را پاک نمی‌کند. بستن با `stop-management.bat` یا `npm run management:stop` انجام می‌شود.

**نمونهٔ محلی به سرور واقعی وصل نیست.** وضعیت‌ها و عملیات روی دادهٔ نمونهٔ مستقل ثبت می‌شوند؛ نشان «محیط آزمایشی محلی» در ورود و همهٔ صفحه‌ها دیده می‌شود. گرفتن پشتیبان، بازیابی، نصب نسخه و تغییر کاربران در این محیط شبیه‌سازی می‌شوند. دادهٔ دستی برنامه در ۵۷۰۰ و دادهٔ ویرایشگر در ۵۷۰۱ جدا هستند.

## آمار و بهبود محصول

صفحهٔ نخست مدیریت، «داشبورد» است. نمودارهای آن از همان گزارش تجمیعی موجود استفاده می‌کنند و ردیابی تازه‌ای جمع‌آوری نمی‌شود. بازهٔ ۷، ۳۰ و ۹۰ روزه، انتخاب شاخص هر نمودار، اشاره یا لمس نمودار و انتخاب روز با صفحه‌کلید و جدول اعداد در دسترس‌اند. محور تعداد از صفر شروع می‌شود؛ روز ناموجود به‌صورت شکاف نمایش داده می‌شود و جمع ناقص نمایش عددی ندارد. صفرِ ثبت‌شده همچنان صفر است.

نمودار میله‌ای شش بخش اول را با معیار قابل‌انتخاب درخواست موفق یا بازشدن مقایسه می‌کند. مجموع همهٔ بخش‌های دارای مقدار هم ذکر می‌شود. نمودار حلقه‌ای، وضعیت فعلی حساب‌های ثبت‌نام‌کامل را نشان می‌دهد و پروفایل‌های فاقد حساب مستقل در آن نیستند. آمار محصول و سلامت سرور جدا دریافت می‌شوند؛ قطع یکی، نمایش موفق بخش دیگر را پنهان نمی‌کند. منابع سرور فقط آخرین مشاهده هستند و نمودار تاریخی برای مصرف پردازنده ساخته نمی‌شود؛ بار پردازنده میانگین یک دقیقه‌ای است، نه درصد مصرف.

گزارش در بازه‌های ۷، ۳۰ و ۹۰ روز تقویمی به وقت تهران، از داده‌های موجود خوانده می‌شود. تعداد فعلی خانواده‌ها، حساب‌های ثبت‌نام‌کامل، پروفایل‌های معرفی‌شده/مدیریت‌شده و وضعیت عضویت جدا هستند. ورود موفقِ ثبت‌شده با کاربر فعال روزانه یکسان نیست؛ نشست ماندگار ممکن است بدون ورود دوباره استفاده شود. تاریخچه‌های قدیمیِ بدون زمان ورود یا تکمیل ثبت‌نام، جدا شمرده می‌شوند.

روند روزانهٔ ساخت خانواده و تکمیل ثبت‌نام از رکوردهای موجود محاسبه می‌شود؛ رکورد حذف‌شده در آن نیست. بازشدن بخش‌ها و درخواست‌های موفق از `support_usage_counters` می‌آیند؛ این جدول فقط ساعت، بخش، نوع عملیات و عدد دارد. درخواست تکراری هم شمرده می‌شود و یک درخواست ممکن است چند رکورد را تغییر دهد. بازشدن آفلاین بخش‌ها ثبت نمی‌شود. اولین شمارندهٔ موجود به معنی اثبات شروع یا کامل‌بودن اندازه‌گیری نیست.

تعداد رکوردهای مالی، کار، خرید و سند از تابع محدود و تجمیعی فعلی خوانده می‌شود. مبلغ، شرح، فایل، پیامک، نام، شماره، شناسهٔ عضو یا خانواده، اطلاعات دستگاه و IP وارد گزارش یا خروجی JSON آن نمی‌شوند. برای این قابلیت، رویداد یا شناسهٔ تازه‌ای از کاربران جمع‌آوری نمی‌شود. همهٔ پرس‌وجوهای گزارش در تراکنش فقط‌خواندنی با سقف زمان اجرا می‌شوند؛ دادهٔ خروجی نیز قرارداد عددی و فهرست کلیدهای مشخص دارد و وجود فیلد اضافه گزارش را رد می‌کند.

در جزئیات حجم داده، تعداد کل کیف پول، سقف بودجه، قبض، اقلام انبار و خرید، غذا و وعدهٔ برنامه‌ریزی‌شده، وسیله، خودرو و سرویس، رویداد تقویم، هدف، پروفایل حیوان و پیامک نیز از فهرست ثابت پرس‌وجوهای `count(*)` خوانده می‌شود. فقط بخش‌های نصب‌شده شمرده می‌شوند؛ جدول ناموجود مقدار `null` دارد و نام جدول یا عبارت پرس‌وجو از مرورگر دریافت نمی‌شود. متن و مبالغ هیچ‌یک از این رکوردها در گزارش قرار نمی‌گیرند.

آمار خطا فقط ورود و ثبت‌نام را پوشش می‌دهد. خطای سرور زیرمجموعهٔ خطاهای همین مسیرهاست و دوباره به مجموع اضافه نمی‌شود. جدول شمارنده یا تابع شمارش ناموجود، به‌صورت «اندازه‌گیری‌نشده» با مقدار `null` گزارش می‌شود؛ شمارندهٔ موجودِ بدون رویداد مقدار صفر با توضیح کمبود سابقه دارد.

بازدید سایت معرفی، کلیک دانلود، کاربران فعال یکتا، بازگشت کاربران، مدت استفاده و آمار مستقل دستیار در داده‌های فعلی اندازه‌گیری نشده‌اند. گزارش این موارد را صفر فرض نمی‌کند. تغییر مستقلی در فایل‌های سایت معرفی یا کد ردیابی کاربران برای این بخش انجام نمی‌شود. مشاهده و دریافت گزارش تجمیعی برای هر سه نقش مدیریت مجاز و همچنان نیازمند نشست مستقل مدیریت است.

## قرارداد اجرای عملیات

پیش‌نمایش کوتاه‌عمر به همان نشست وابسته است. تأیید رمز، در تولید احراز دومرحله‌ای، و برای عملیات حساس تکرار شناسهٔ مقصد لازم است. نشست با کوکی HttpOnly، SameSite=Strict و در تولید Secure نگه داشته می‌شود. مبدأ دقیق، CSRF، محدودیت تلاش و انقضا سمت سرور بررسی می‌شوند.

عملیات تغییردهنده هم در سرویس وب و هم در میزبان قفل می‌شوند. شناسهٔ تکراری، همان درخواست ثبت‌شده را برمی‌گرداند. عملیات قطع‌شده پس از شروع دوبارهٔ سرویس خودکار تکرار نمی‌شود؛ وضعیت فعلی و سابقه باید بررسی شوند. پشتیبان زمان‌بندی‌شده نیز همان قفل میزبان را می‌گیرد.

وب‌سرویس با کاربر محدود اجرا می‌شود. sudoers فقط `/usr/local/sbin/khaneyar-management-worker` را **بدون آرگومان** مجاز می‌کند. راه‌انداز محیط را پاک و Python را با `-I` اجرا می‌کند. درخواست JSON با قرارداد مشترک دوباره اعتبارسنجی می‌شود. دستور shell، مسیر فایل، SQL یا URL دلخواه از مرورگر پذیرفته نمی‌شود. کد و پیکربندی worker متعلق به root هستند.

## پشتیبان و بازیابی

API برای ثبت وضعیت سازگار کوتاه‌مدت متوقف می‌شود. پشتیبان شامل dump سفارشی PostgreSQL، مشخصات و هش رمز نقش محدود اتصال برنامه، آپلودهای محلی، تنظیمات و کلید رمزنگاری موجود، فایل‌های Compose مورد استفاده، PWA و تصویر دقیق Docker برنامه است. برای هر فایل SHA-256 ثبت می‌شود. پشتیبان‌های ناقص در فهرست کامل‌ها ظاهر نمی‌شوند.

بازیابی ابتدا هش و ساختار را کنترل و تصویر قدیمی را بارگذاری می‌کند، سپس از وضعیت فعلی یک پشتیبان تازه می‌گیرد. از شروع بکاپ حفاظتی تا پایان بازیابی، API متوقف می‌ماند. dump در یک تراکنش بازگردانده می‌شود؛ نقش محدود، فایل‌ها، تنظیمات و تصویر همان نسخه نیز برمی‌گردند. مالکیت آپلودها برای UID 10001 کانتینر بازسازی می‌شود. شکست بازیابی دیتابیس API را متوقف نگه می‌دارد؛ پشتیبان حفاظتی حفظ می‌شود. بررسی سلامت پس از شروع نسخهٔ بازیابی‌شده انجام می‌شود.

این اتصال برای استقرار موجود پروژه با PostgreSQL 17 در Compose، فایل محلی و کاربر کانتینر 10001 نوشته شده است. ذخیره‌سازی S3 به بکاپ مستقل اشیای همان مخزن نیاز دارد؛ در آن حالت ساخت پشتیبان «کامل» متوقف می‌شود. پشتیبان‌ها خودکار حذف نمی‌شوند. timer روزانه ساعت ۰۲:۰۰ UTC با حداکثر پنج دقیقه جابه‌جایی اجرا می‌شود.

دانلود پشتیبان فقط برای مالک و پس از احراز دوباره است. فایل خروجی موقت خصوصی پس از ارسال حذف می‌شود. فایل دانلودشده شامل اطلاعات و کلید بازیابی است. خود پایگاه هویت مدیریت در پشتیبان خانواده قرار ندارد؛ بازیابی نسخهٔ برنامه نباید مالک پنل را از حساب خود خارج کند. از `/var/lib/khaneyar-management` و پیکربندی مدیریت به‌صورت خصوصی و مستقل نگهداری شود.

## انتشار و نصب

فقط مخزن رسمی `mojtabaaomidvar/FinanicalManagement` پذیرفته می‌شود. tag قالب ثابت دارد؛ بستهٔ `.tgz` یا `.tar.gz` با `SHA256SUMS` یا فایل هش متناظر بررسی می‌شود. آرشیوهای دارای traversal، لینک، فایل ویژه یا حجم بیش از حد رد می‌شوند. نصب‌کنندهٔ داخل بستهٔ بررسی‌شده اجرا می‌شود و قبل از آن بکاپ کامل مدیریت گرفته می‌شود. مسیر منبع استخراج‌شده برای buildهای بعدی نگه داشته می‌شود.

نصب‌کنندهٔ هر نسخه مسئول بررسی schema و مهاجرت همان نسخه است؛ پنل `alembic upgrade head` عمومی، downgrade حدسی یا بازگردانی خودکار گسترده اجرا نمی‌کند. بازگشت از بخش پشتیبان‌ها و با انتخاب نسخهٔ سازگار انجام می‌شود.

## آماده‌سازی تولید

### به‌روزرسانی داشبورد 0.2.0

بستهٔ `management-v0.2.0` به‌روزرسانی فقط رابط پنل نصب‌شدهٔ `0.1.0` است. راه‌انداز `upgrade-management-web.py`، ساخت ورودی، هش فایل‌های رابط قبلی و کد اجرایی نصب‌شده را بررسی می‌کند؛ نصب دست‌کاری‌شده یا نسخهٔ ناسازگار پیش از جابه‌جایی رد می‌شود. رابط قبلی در `/opt/khaneyar-management/web-backups/` حفظ می‌شود و شکست بررسی سلامت، آن را بازمی‌گرداند. فایل‌های asset انتشار قبل برای تب‌های باز نیز نگه داشته می‌شوند. نصب مجدد همین نسخه پس از تطبیق هش‌ها بدون تغییر خاتمه می‌یابد.

این به‌روزرسانی پایگاه هویت، رمز، TOTP، نشست‌ها، تنظیمات nginx و sudoers، سرویس API، دیتابیس و برنامهٔ خانوادگی را تغییر نمی‌دهد. مالک تازه ساخته نمی‌شود و سرویس مدیریت restart نمی‌شود. پس از نصب، صفحهٔ مدیریت را تازه کنید. نصب تازه همچنان از بستهٔ `0.1.0` انجام می‌شود؛ برای ارتقای آن از راه‌انداز `0.2.0` استفاده کنید.

نصب پنل از بستهٔ مستقل مدیریت و کنسول سرور انجام می‌شود. فایل‌های نصب در `backend/deploy/management/` هستند. برای ساخت از منبع، `npm run management:build` را اجرا کنید؛ خروجی `.local-test/management-web` فقط رابط مدیریت است و هیچ فایل محیطی یا داده‌ای ندارد.

### نصب روی دامنهٔ فعلی پشتیبانی

نسخهٔ مستقل مدیریت `management-v0.1.0` برای نشانی `https://supp.khaanehyar.ir/management/` طراحی شده است. شمارهٔ برنامهٔ خانوادگی مستقل باقی می‌ماند. ریشهٔ همین دامنه، پنل پشتیبانی موجود است؛ نصب‌کننده تنها یک include مشخص به میزبان HTTPS موجود اضافه می‌کند. وجود مسیر متداخل، کانفیگ ناشناخته یا لینک متفاوت پیش از نصب رد می‌شود. کانفیگ قبلی در `/var/backups/khaneyar/management-install/` ذخیره می‌شود و شکست اعتبارسنجی nginx، فایل‌های مسیر پشتیبانی را برمی‌گرداند.

بسته از کنسول VNC و با کاربر root نصب می‌شود. راه‌انداز رسمی، هش آرشیو را پیش از استخراج بررسی می‌کند. هنگام نصب، رمز تازهٔ مالک با نام کاربری `admin` در کنسول دریافت می‌شود و کلید ورود دومرحله‌ای همان‌جا نمایش داده می‌شود؛ آن را در برنامهٔ رمزساز ثبت کنید. اطلاعات ورود محیط محلی یا اپراتور پشتیبانی به مدیریت منتقل نمی‌شوند. نصب تازه روی سرویس مدیریت موجود انجام نمی‌شود و از تغییر هویت نصب قبلی جلوگیری می‌شود.

برای نصب از منبع و ساخت مستقلِ بررسی‌شده:

```bash
bash /path/to/reviewed-source/backend/deploy/management/install-management.sh \
  /path/to/reviewed-source \
  /path/to/management-web \
  https://supp.khaanehyar.ir shared-support
```

نسخه پس از نصب از `https://supp.khaanehyar.ir/management/version.json` قابل بررسی است. ساخت از مسیرهای نسبی برای فایل‌های رابط استفاده می‌کند و هم در ریشهٔ نمونهٔ محلی و هم زیر مسیر مدیریت کار می‌کند. سرویس قبل از بارگذاری nginx با نشست ناشناس و حالت `production` بررسی می‌شود. پنل از اطلاعات واقعی میزبان می‌خواند؛ نصب این بسته، API یا PWA خانوادگی را ارتقا نمی‌دهد و مهاجرت دیتابیس ندارد. کلیدهای تعمیرات، ثبت‌نام و دستیار تا زمان استقرار API سازگار طبق توضیح زیر غیرفعال می‌مانند.

روی VPS، دامنهٔ مدیریت مانند `admin.khaanehyar.ir` و گواهی معتبر آن باید آماده باشند. Python 3.11 یا جدیدتر با venv، Docker Compose، nginx، certbot، sudo و systemd پیش‌نیازند. سپس از کنسول سرور و با مسیرهای بستهٔ بررسی‌شده اجرا کنید:

```bash
bash /path/to/reviewed-source/backend/deploy/management/install-management.sh \
  /path/to/reviewed-source \
  /path/to/management-web \
  https://admin.khaanehyar.ir
```

نصب‌کننده از بازنویسی نصب یا کانفیگ nginx موجود خودداری می‌کند. یک کاربر سیستم محدود، محیط Python مستقل، worker متعلق به root، sudoers محدود، سرویس مدیریت، timer خاموش و میزبان nginx جدا می‌سازد. رمز مالک در کنسول دریافت و کلید TOTP برای ثبت در برنامهٔ رمزساز فقط همان‌جا نشان داده می‌شود. سرویس وب فقط روی loopback پورت ۵۷۱۰ است؛ TLS در nginx خاتمه می‌یابد.

اتصال کنترل‌های تعمیرات/ثبت‌نام/دستیار نیازمند دو جزء در **انتشار بررسی‌شدهٔ برنامه** است: middleware `app.core.managed_runtime` و override آماده‌شدهٔ `docker-compose.management.json`. در `COMPOSE_FILE` فعلی، بدون حذف overrideهای قبلی، این فایل را هم اضافه و API سازگار را recreate کنید. `KHANEYAR_RUNTIME_FILE=/run/khaneyar-management/runtime.json` و mount فقط‌خواندنی همین پوشه باید برقرار باشند. پاسخ `/api/v1/healthz` فقط در اتصال فعال، `managed_runtime: v1` می‌دهد. تا آن زمان این کنترل‌ها در پنل غیرفعال‌اند؛ تنظیمات درگاه و OTP قرارداد فعلی خود را دارند.

تنظیمات خارج فهرست مجاز، کلید رمزنگاری اسناد و تنظیمات پنل پشتیبانی از ویرایشگر تنظیمات مدیریت تغییر نمی‌کنند. ویرایش متن‌های ثابت مدیریت نیز مثل متن‌های دیگر در ابزار محلی کپی انجام می‌شود؛ پنل مدیریت ویرایشگر آزاد فایل سرور ندارد.

پس از اعمال متن‌های مدیریت در ویرایشگر محلی، `npm run management:build` و سپس تازه‌سازی صفحهٔ مدیریت، رابط مستقل آن را به‌روز می‌کند. `sandbox:refresh` همچنان برای نسخهٔ دستی خود برنامه است.

## بررسی توسعه

### تاریخچهٔ محلی نسخه‌ها

در ساخت مدیریت `0.4.0`، صفحهٔ نسخه‌ها دو نمای «تغییرات نسخه‌ها» و «بسته‌های نصب» دارد. یادداشت‌ها از `release-history.json` در زمان ساخت وارد می‌شوند و برای خواندن به اینترنت یا GitHub نیاز ندارند. وضعیت نصب از میزبان خوانده می‌شود؛ شمارهٔ ثابت health شناسهٔ انتشار API فرض نمی‌شود. خرابی دریافت وضعیت، یادداشت‌های محلی را پنهان نمی‌کند. برنامهٔ `0.15.0` فقط یادداشت‌های عمومی خود را از بخش درباره نمایش می‌دهد؛ خروجی فنی مدیریت وارد PWA نمی‌شود. [گزارش بسته و نصب](deployment-history-2026-11-28.md) محدودیت‌ها و پایهٔ دقیق نصب را ثبت می‌کند.

تغییرهای ساخت محلی `0.3.0-dev` شامل آمار مستقل AI، اصلاح طبقه‌بندی آفلاین، پیکربندی امکانات، سقف مصرف و تفکیک نسخه‌ها در [گزارش ۲۶ نوامبر](ai-usage-offline-controls-2026-11-26.md) ثبت شده‌اند. این ساخت هنوز انتشار یا نصب تولید نیست؛ به‌روزرسانی وبِ `0.2.0` برای انتقال این تغییرهای بک‌اند کافی نیست.

```powershell
npm run management:test
npm run management:build
npm run management:browser-check
npm run copy:studio:coverage
python -m ruff check backend/app/management backend/app/core/managed_runtime.py backend/management-worker.py
```

تست‌های مدیریت مسیر صریح و جدا دارند و `backend/tests/conftest.py` و دیتابیس برنامه را بار نمی‌کنند. بررسی مرورگر یک سرویس نمونهٔ مستقل روی پورت موقت می‌سازد، به همان مبدأ محدود می‌شود و screenshot و نتیجه را زیر `.local-test/management-browser/` ذخیره می‌کند. این بررسی، جای آزمون نصب و عملیات واقعی Docker/systemd روی میزبان Linux را نمی‌گیرد.
