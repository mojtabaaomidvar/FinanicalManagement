# تحویل استقرار — ۲۰۲۶-۱۱-۱۱ / ۱۴۰۵-۰۸-۲۰

API و PWA خانه‌یار روی سرور تازهٔ پارس‌پک، `193.138.77.239` با Ubuntu 24، فعال‌اند. کاربر ثبت‌نام و ورود واقعی را تأیید کرد. این گزارش وضعیت همین استقرار را ثبت می‌کند؛ اسناد کوچ‌های قبلی برای تاریخچه حفظ شده‌اند.

## راستی‌آزمایی

- `https://api.khaanehyar.ir/api/v1/auth/config` و `https://pwa.khaanehyar.ir/` پاسخ ۲۰۰ دادند. در زمان بررسی، `otp_enabled=false` و `password_reset_enabled=false` بود؛ ثبت‌نام و ورود بدون سرویس پیامک ممکن بود.
- HTML، JS و CSS اصلی، manifest، service worker و وابستگی Workbox، فونت فارسی و آیکون نصب ۵۱۲ همگی از بیرون پاسخ ۲۰۰ دادند. JS ساخته‌شده مبدأ درست API را دارد؛ service worker فایل‌های نسخهٔ نصب‌شده را precache می‌کند و درخواست‌های API را `NetworkOnly` نگه می‌دارد.
- preflight مسیر `POST /api/v1/auth/register` برای Origin برابر `https://pwa.khaanehyar.ir` موفق بود؛ POST و Content-Type مجاز بودند.
- بررسی‌های بیرونی با اعتبارسنجی عادی TLS انجام شدند؛ برای عبور از کش DNS شبکه، `curl --resolve` به IP تازه استفاده شد، بدون غیرفعال‌کردن اعتبارسنجی گواهی.
- کاربر پس از نصب PWA، ثبت‌نام و ورود را تأیید کرد. بررسی‌های خودکار هیچ حساب یا دادهٔ تولیدی نساختند.
- پس از نصب سایت معرفی، صفحهٔ اصلی، `www`، صفحهٔ دریافت، CSS، فونت و service worker با TLS معتبر از IP تازه پاسخ ۲۰۰ دادند؛ عنوان HTML همان سایت خانه‌یار بود. HTTP دامنهٔ اصلی با ۳۰۱ به HTTPS منتقل شد. هدر service worker نیز `no-store, must-revalidate` بود.
- اجرای دستی بکاپ و سلامت فشرده‌سازی از تصویر کنسول تأیید شدند. پس از ساخت دیتابیس موقت `khaneyar_restore_check_20261111` با `createdb`، بارگذاری SQL بکاپ `db-20261111-083906.sql.gz` موفق بود؛ تصویر VNC خروجی‌های `CREATE POLICY`، `ALTER TABLE` و `RESTORE OK` را نشان داد. تصویر بعدی، خروجی دو پرس‌وجوی همین دیتابیس را تأیید کرد: `alembic_version` برابر `0011` و تعداد جدول‌های `public` برابر ۲۸ است.
- دیتابیس موقت پس از بررسی ساختار، با دستور محافظت‌شدهٔ `dropdb` حذف شد؛ تصویر VNC خروجی `TEMP DB REMOVED` را تأیید کرد.
- آرشیو `uploads-20261111-083906.tar.gz` با `tar` در پوشهٔ خصوصی ساخته‌شده با `mktemp` استخراج شد؛ تصویر VNC خروجی `UPLOADS RESTORE OK` و شمارش `files=0` و `dirs=1` در مسیر استخراج‌شدهٔ `uploads` را تأیید کرد. این آرشیو در زمان همان بکاپ فقط یک پوشهٔ خالی داشته است؛ قابلیت استخراج تأیید شد، اما نمونهٔ فایل واقعی برای آزمون بازیابی محتوای فایل در آن وجود نداشت.
- پوشهٔ موقت ساخته‌شده با قالب `/tmp/khaneyar-restore.XXXXXX` پس از آزمون استخراج حذف شد؛ آخرین تصویر VNC خروجی `TEMP FILES REMOVED` را تأیید کرد.

## باقی‌مانده

- **مشاهدهٔ نخستین اجرای cron:** اجرای دستی بکاپ و فعال‌بودن cron تأیید شده‌اند؛ نخستین اجرای زمان‌بندی‌شده هنوز مشاهده نشده است.
- **انتخاب کاربر دربارهٔ مقصد بکاپ:** کاربر مرحلهٔ بکاپ خارج از سرور را نخواست؛ این کار از ادامهٔ فعلی حذف شد و مقصد یا سرویس تازه‌ای ایجاد نمی‌شود.
- **APK debug قدیمی:** فایل قدیمی debug در `android/app/build/outputs/apk/debug/app-debug.apk` همچنان به `https://finanical-management.vercel.app` اشاره می‌کند و نباید منتشر شود. فایل‌های APK در گیت نیستند.
- **SSH مدیریتی:** کلید عمومی از طریق VNC روی سرور نصب شد، اما اتصال پورت ۲۲ پس از تأیید ثبت نهایی فایروال هم پیش از احراز هویت timeout می‌شود. علت تأیید نشده است؛ نصب سایت و بکاپ روزانه از VNC تکمیل شدند و دسترسی SSH همچنان نیازمند رفع مشکل است.

- تغییرات commit‌نشدهٔ `backend/Dockerfile` و `backend/deploy/docker-compose.yml` از ادامهٔ قبلی باقی مانده‌اند: timeout/retry دانلود pip و آرگومان قابل‌تنظیم `PIP_INDEX_URL`. این گزارش آن فایل‌ها را تغییر نداد.

- `capacitor.config.ts` مبدأ درست `https://pwa.khaanehyar.ir` را دارد و اکنون تنظیم تولیدشدهٔ داخل APK هم با آن همگام است. فایل `android/app/build.gradle` و metadata انتشار به نسخهٔ ۱٫۲ به‌روز شدند؛ صفحهٔ دریافت نیز نسخهٔ درست، اندروید ۷ به بالا و منابع رسمی وب‌سایت/گیت‌هاب را معرفی می‌کند. این تغییرات روی شاخهٔ `codex/android-1-2` ثبت شدند؛ `main` محلی و GitHub نیز به همان commit انتشار همگام شدند و شاخهٔ جاری `codex/android-1-2` حفظ شد.

## اصلاح مجوز ویرایش تراکنش در ادامهٔ استقرار

- کد و تست‌های اصلاح روی شاخهٔ `codex/transaction-edit-authorization` ثبت و push شده‌اند. این اصلاح فقط بک‌اند را تغییر می‌دهد؛ APK نسخهٔ ۱٫۲ منتشرشده همچنان قابل استفاده است و APK تازه لازم نیست.
- در مسیر ویرایش تراکنش، `owner` و `admin` همهٔ تراکنش‌های خانوادهٔ خود را ویرایش می‌کنند؛ `member` فقط ردیفی را که `member_id` فعلی آن برابر شناسهٔ خودش است. هدف غیرمجاز مانند مسیر حذف با `404` رد می‌شود و دادهٔ آن تغییر نمی‌کند.
- عضو عادی نمی‌تواند تراکنش خودش را به عضو دیگری نسبت دهد؛ این reassignment با `403` رد می‌شود. مدیر می‌تواند عضو منتسب را بین اعضای همان خانواده تغییر دهد.
- ردیف هنگام بررسی مجوز با `SELECT FOR UPDATE` قفل می‌شود و قفل تا commit می‌ماند؛ بنابراین reassignment هم‌زمان مدیر نمی‌تواند میان بررسی مجوز و ذخیرهٔ ویرایش عضو رخ دهد.
- سه فایل تست این رفتار را پوشش می‌دهند: `backend/tests/test_known_gaps.py` شکاف #۵ را از xfail به regression تبدیل کرده، `backend/tests/test_role_authorization.py` حالت‌های مجاز و غیرمجاز و دادهٔ ذخیره‌شده را بررسی می‌کند، و `backend/tests/test_transaction_edit_concurrency.py` با دو Session واقعی، زمینهٔ RLS و `lock_timeout` کوتاه، قفل و رد ویرایش عضو قبلی پس از reassignment را می‌سنجد.
