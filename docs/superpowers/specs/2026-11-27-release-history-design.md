# تاریخچهٔ نسخه‌های خانه‌یار

## وضعیت

طرح محصول و معماری در سه بخش به تأیید مالک رسیده است. این سند جزئیات همان تصمیم‌ها را برای بازبینی نهایی ثبت می‌کند؛ تغییر حاضر فقط مستندات است.

## مسئله

کاربران باید بتوانند تغییرات نسخه‌های برنامه را بفهمند و بعداً دوباره به آن‌ها مراجعه کنند. مالک سامانه نیز به تاریخچهٔ فنی نسخه‌های مستقل PWA، API و پنل مدیریت در پنل مدیریت نیاز دارد. این اطلاعات نباید با سابقهٔ عملیات مدیران یا وضعیت نصب‌شدهٔ واقعی اشتباه شود.

تاریخچه نباید برای خواندن، ساخت یا کارکرد آفلاین به GitHub یا سرویس انتشار خارجی وابسته باشد؛ محل میزبانی و روش انتشار ممکن است در آینده تغییر کند.

## انتخاب‌های تأییدشده

- تاریخچه برای همهٔ کاربران قابل‌دسترسی است؛ یادداشت عمومی فقط تغییرهای اثرگذار بر کاربر را با زبان ساده توضیح می‌دهد.
- نمای پنل مدیریت علاوه بر یادداشت‌های عمومی، اطلاعات فنی غیرمحرمانهٔ PWA، API و پنل مدیریت را نشان می‌دهد.
- تاریخچه در یک منبع محلی و نسخه‌دار نگه‌داری می‌شود. برنامه و پنل مدیریت دادهٔ خود را همراه ساخت می‌گیرند؛ درخواست زمان اجرا برای دریافت تاریخچه لازم نیست.
- برنامه تاریخچه را از «تنظیمات ← درباره» باز می‌کند. بعد از نصب به‌روزرسانی، یک پیام غیرمسدودکننده و یک‌باره پیوند تغییرات نسخهٔ تازه را می‌دهد.
- صفحهٔ «نسخه‌ها»ی مدیریت دو نمای جدا دارد: «تغییرات نسخه‌ها» و «بسته‌های نصب». «سابقه»ی موجود همچنان فقط عملیات، رویدادها و ورودهای مدیریت را نشان می‌دهد.
- تاریخ انتشار، یادداشت انتشار و نسخهٔ نصب‌شده سه دادهٔ جدا هستند. نمایش یادداشت یا وجود یک بستهٔ آماده، مدرک نصب موفق نیست.

## منبع داده

یک فهرست ساختاریافته در ریشهٔ پروژه، با نام `release-history.json`، منبع اصلی نسخه‌هاست. قرارداد مفهومی زیر فقط شکل داده را نشان می‌دهد و سابقهٔ واقعی یک انتشار نیست:

```json
{
  "schema_version": 1,
  "releases": [
    {
      "id": "pwa-0.12.0",
      "component": "pwa",
      "version": "0.12.0",
      "notes_status": "partial",
      "user_notes": {
        "summary": "",
        "features": [
          { "id": "example-feature", "text": "" }
        ],
        "improvements": [],
        "fixes": []
      },
      "technical_notes": []
    }
  ]
}
```

`component` یکی از `pwa`، `api` یا `management` است؛ `version` نسخهٔ رسمی همان جزء با قالب سه‌بخشی است. `released_on` تاریخ میلادی با قالب `YYYY-MM-DD` دارد و در صورت نبود مدرک حذف می‌شود، نه اینکه تخمین زده شود. `user_notes` برای PWA یک شیء شامل خلاصه و سه فهرست تغییر است و برای جزءهای دیگر می‌تواند `null` باشد. اعضای فهرست‌های عمومی و `technical_notes` همگی شیء با دو فیلد `id` و `text` هستند؛ `text` فقط متن ساده است و HTML یا کد اجرایی رندر نمی‌شود.

اعتبارسنجی manifest باید ساختار و `schema_version`، نوع جزء، قالب نسخه و تاریخ، نوع فهرست‌ها و یکتایی ترکیب جزء/نسخه را کنترل کند. یک بررسی انتشار نیز باید مانع ساخت رسمی جزءی شود که برای نسخهٔ در حال انتشار رکورد معتبر ندارد.

هر رکورد یک `id` ثابت به‌شکل جزء و نسخه دارد؛ مثلاً `pwa-0.12.0`. شناسهٔ جایگاه خلاصه از `id` رکورد و پسوند `.summary` ساخته می‌شود. `id` هر مورد از تغییرها در محدودهٔ همان رکورد یکتا است و همراه پسوند `.notes.`، جایگاه متن آن را مشخص می‌کند؛ مثلاً `pwa-0.12.0.notes.example-feature`. شناسه‌ها با جابه‌جایی مورد، تغییر دسته، ترجمه یا خالی‌شدن متن عوض نمی‌شوند و شمارهٔ موقعیت آرایه جای شناسه را نمی‌گیرد. یادداشت کامل یا ناقص با فیلد ساختاری `notes_status` و مقدار `complete` یا `partial` تعیین می‌شود؛ خالی‌شدن متن در ویرایشگر، وضعیت انتشار را تغییر نمی‌دهد. نسخه‌های تاریخیِ دارای مدرک ناقص می‌توانند `partial` باشند؛ رکورد نسخهٔ در حال انتشار باید `complete` باشد.

در هر جزء، ترتیب عددی سه بخش نسخه ملاک است؛ ترتیب رشته‌ای یا تاریخِ احتمالاً ناموجود ملاک نیست. تاریخچهٔ PWA تا نسخهٔ همان ساخت محدود می‌شود تا برنامهٔ قدیمی قابلیت نسخهٔ بعدی را به‌عنوان تغییر قابل‌استفادهٔ خودش نشان ندهد. بازسازی‌های مستقل یک بسته مانند `r1`، بدون تغییر نسخهٔ محصول، رکورد تکراری PWA نمی‌سازند؛ اصلاح بسته در یادداشت فنی انتشار مربوط ثبت می‌شود.

ساخت PWA فقط نمای عمومی رکوردهای PWA را در bundle یا دارایی قابل پیش‌کش خود قرار می‌دهد؛ اطلاعات API و مدیریت وارد خروجی PWA نمی‌شوند. ساخت مستقل مدیریت، رکوردهای همهٔ اجزا و یادداشت‌های فنی را در دارایی خودش قرار می‌دهد. دارایی‌های تاریخچه بخشی از خروجی‌های بررسی‌شده و هش‌دارِ همان انتشار هستند؛ API جداگانه یا درخواست GitHub برای نمایش تاریخچه لازم نیست.

هر دو خروجی، تصویری از منبع در زمان ساخت خود دارند. اگر بعداً فقط PWA ارتقا یابد، تاریخچهٔ داخل پنل قدیمی خودکار تازه نمی‌شود؛ نسخهٔ فعالِ فاقد رکورد باید با توضیح «یادداشت این نسخه در این ساخت موجود نیست» نشان داده شود. تکمیل فهرست پنل همراه انتشار بعدی خودش انجام می‌شود و به دریافت زنده از اینترنت وابسته نیست.

هر چیزی که داخل bundle وب یا دارایی استاتیک مدیریت قرار گیرد از نظر فنی قابل‌دریافت است، حتی اگر رابط مدیریت آن را پشت ورود نشان دهد. بنابراین یادداشت فنی می‌تواند نام قابلیت، مرز سازگاری، نسخهٔ مهاجرت یا تغییر معماری کلی را شرح دهد، اما نباید شامل رمز، نشانی خصوصی، اطلاعات شخصی، روش بهره‌برداری از آسیب‌پذیری یا جزئیات عملیاتی محرمانه باشد. چنین جزئیاتی اصلاً عضو تاریخچهٔ انتشار نیستند؛ اگر روزی به سابقهٔ محرمانه نیاز شد، آن نیاز سامانهٔ جداگانه و احراز‌شده می‌خواهد.

نسخه‌های آزمایشی و شناسه‌های build در تاریخچهٔ رسمی وارد نمی‌شوند. شمارهٔ نسخه از منبع مستقل هر جزء خوانده می‌شود و نباید از نسخهٔ جزء دیگری استنتاج شود.

## تجربهٔ برنامه

در «تنظیمات ← درباره»، عملی با نام «تاریخچهٔ نسخه‌ها» فهرست انتشارهای PWA را از جدید به قدیم باز می‌کند. هر ردیف نسخه و تاریخِ تأییدشده را دارد و جزئیات همان انتشار، تغییرها را بر اساس قابلیت تازه، بهبود و رفع اشکال گروه‌بندی می‌کند. اگر تاریخ یا شرح یک نسخه از سوابق موجود قابل بازیابی نباشد، رابط آن کمبود را صریح می‌گوید و اطلاعات ساختگی نشان نمی‌دهد.

داده همراه برنامه است و خواندن آن به اینترنت یا API احراز هویت نیاز ندارد؛ مسیر رابط همان بخش «درباره» برای کاربران برنامه است. تاریخچه با بارگذاری عادی برنامه در دسترس است. اگر رابط به‌صورت جداگانه بارگذاری شود، حالت انتظار آن نیز روشن است؛ خالی‌بودن تاریخچه و خطای داده نباید جلوی بازشدن برنامه را بگیرد.

برای پیام پس از به‌روزرسانی:

- فقط پس از فعال‌شدن نسخهٔ تازه از جریان update خود برنامه نمایش داده شود؛ نصب نخست یا بازشدن معمول برنامه نباید به‌عنوان به‌روزرسانی جا زده شود.
- پیام غیرمسدودکننده باشد و کاربر را به یادداشت همان نسخه ببرد؛ انتخاب آن هیچ تغییری در داده یا تنظیمات ایجاد نمی‌کند.
- نمایش هر نسخه در همان مرورگر یا فضای ذخیره‌سازی برنامه حداکثر یک‌بار انجام شود. نشانگر نسخهٔ دیده‌شده محلی و غیرحساس است و به سرور، حساب یا analytics فرستاده نمی‌شود. پاک‌شدن دادهٔ مرورگر یا نصب روی دستگاه دیگر، این سابقهٔ محلی را منتقل یا بازیابی نمی‌کند.
- اگر ذخیره‌سازی محلی در دسترس نباشد، پیام خودکار نمایش داده نشود تا در هر بازشدن تکرار نشود؛ تاریخچه همچنان از مسیر «درباره» در دسترس بماند.
- ردکردن پیام، به‌روزرسانی را عقب نمی‌اندازد و امکان مراجعهٔ همیشگی از «درباره» باقی می‌ماند.

پیش از اجرای `applyUpdate`، نسخهٔ فعلی در یک نشانگر محلیِ به‌روزرسانی ثبت می‌شود. در شروع بعدی، فقط وجود این نشانگر و بزرگ‌تر بودن نسخهٔ فعال اجازهٔ اعلان می‌دهد؛ reload همان نسخه و بازگشت به نسخهٔ پایین‌تر اعلان نمی‌سازند. اگر service worker هنوز نسخهٔ قبلی را اجرا می‌کند، نشانگر تا فعال‌شدن نسخهٔ تازه نگه داشته می‌شود. نمایش و بستن اعلان، نشانگر مصرف‌شده را پاک می‌کند. پیش از نمایش، رکورد نسخهٔ مقصد و دسترسی ذخیره‌سازی بررسی می‌شوند. رفتار باید در نصب وب و پوستهٔ Android که همان PWA را باز می‌کند سازگار بماند. در این مرحله، ارتقا فقط از مسیر update موجود تشخیص داده می‌شود؛ تشخیص تغییر در محیط فاقد service worker به آن افزوده نمی‌شود.

## تجربهٔ پنل مدیریت

نمای «تغییرات نسخه‌ها» رکوردهای PWA، API و مدیریت را بر اساس جزء دسته‌بندی می‌کند و از هر رکورد، شرح عمومی و یادداشت فنی را نشان می‌دهد. بخش نسخه‌های نصب‌شده از endpoint فعلی وضعیت سامانه خوانده می‌شود؛ فقط انطباق نسخهٔ نصب‌شده با رکورد همان جزء می‌تواند برچسب «نصب‌شده» بگیرد.

نسخهٔ ثابت پکیج API در پاسخ سلامت، مانند `0.1.0`، معادل شناسهٔ انتشار API نیست. در نبود شناسهٔ انتشار قابل‌تأیید برای آن جزء، وضعیت تطبیق «نامشخص» می‌ماند؛ نه نسخهٔ PWA و نه جدیدترین یادداشت جای آن را پر نمی‌کند. خرابی درخواست وضعیت نصب‌شده، تاریخچهٔ محلی را پنهان نمی‌کند.

نمای «بسته‌های نصب» و عملیات فعلی دریافت/نصب بدون تغییر رفتاری باقی می‌مانند. تاریخچه نه job جدید می‌سازد، نه اجرای نصب را آغاز می‌کند و نه جای audit/operation history را می‌گیرد. نقش‌های پنل فقط برای بازکردن رابط مدیریت لازم‌اند؛ خود تاریخچه عمومی است.

## بازسازی نسخه‌های منتشرشده

پیش از پرکردن manifest، فهرست انتشارهای رسمی از اسناد نسخه‌گذاری، گزارش‌های انتشار/نصب و منابع محلیِ قابل‌بررسی استخراج و برای هر جزء جداگانه تطبیق داده می‌شود. از GitHub یا شبکه در runtime استفاده نمی‌شود. دادهٔ سابقه فقط از مدرک قابل‌ردیابی وارد می‌شود؛ تاریخ، نسخه یا جزئیات گمشده حدس زده نمی‌شود.

اگر نسخه‌ای به‌طور مستقل قابل‌تأیید است اما یادداشت کامل آن در سابقه نیست، نسخه می‌تواند در فهرست بماند و کمبود یادداشت به کاربر اعلام شود. اگر شمارهٔ خود نسخه یا تعلق آن به انتشار رسمی تأیید نشود، رکورد منتشر نمی‌شود تا زمانی که مدرک یا تأیید مالک فراهم شود.

در منبع فعلی این شاخه، `package.json` نسخهٔ `0.11.0` دارد؛ شواهد عملیاتی قبلی سرور PWA را `0.12.0` نشان می‌دهند. این دو مقدار به‌تنهایی تاریخچهٔ انتشار را کامل نمی‌کنند. تطبیق نسخه‌های موجود و ثبت PWA، API و مدیریت باید پیش از ساخت manifest در پیاده‌سازی بازبینی شود؛ هیچ‌کدام جای دیگری را حدس نمی‌زند.

## حریم خصوصی و محدوده

- نمایش تاریخچه دادهٔ تازه‌ای از کاربر جمع نمی‌کند و endpoint یا migration دیتابیس تازه لازم ندارد.
- متن عمومی فقط اثر روی محصول را توضیح می‌دهد؛ گزارش‌های خصوصی نصب و پشتیبان، شماره‌ها و جزئیات پیکربندی میزبان به تاریخچه منتقل نمی‌شوند.
- وابستگی زمان اجرای تاریخچه به GitHub حذف است. فرایند فعلی دریافت بستهٔ نصب در پنل که به GitHub متصل است خارج از این تغییر می‌ماند؛ انتخاب منبع جایگزین برای خود بسته‌های نصب تصمیم و کار جداگانه است.
- تاریخچه فقط دربارهٔ انتشارهای رسمی اجزای بالا است؛ تغییرهای آزمایشی و رخدادهای یک سرور/مدیر در آن ثبت نمی‌شوند.

## دسترس‌پذیری و متن

رابط فارسی RTL و واکنش‌گرا است، با ناوبری صفحه‌کلید، تمرکز دیداری، عنوان‌های معنادار و وضعیت‌های خالی/خطا. همهٔ متن‌های ثابت برنامه و مدیریت، شامل خلاصه‌ها و متن یادداشت‌های تاریخی، پیام update و حالت‌های خطا و خالی، باید در copy workbench کشف‌پذیر و قابل‌ویرایش باشند. چون JSON مسیر استخراج عادی نوشته‌ها نیست، اتصال صریح استخراج/اعمال و پیش‌نمایش برای جایگاه‌های متنی این فایل لازم است. هر دو نمایش برنامه و مدیریت به همان جایگاه منبع وصل می‌شوند؛ ویرایش یک یادداشت، نسخهٔ دیگری را تغییر نمی‌دهد.

شمارهٔ نسخه، تاریخ، نوع جزء، شناسه‌های ثابت و `notes_status` قرارداد داخلی هستند و وارد ویرایش متن نمی‌شوند. جایگاه متن پس از ترجمه به انگلیسی یا ذخیرهٔ رشتهٔ خالی هم قابل انتخاب و ویرایش می‌ماند. این اتصال از جایگاه مشخص منبع استفاده می‌کند و جایگزینی سراسری رشته‌ها روی دادهٔ کاربر مجاز نیست.

## معیارهای پذیرش

1. برنامهٔ رسمی فقط یادداشت PWA را نمایش می‌دهد؛ یادداشت فنی API یا مدیریت وارد خروجی قابل‌دریافت PWA نشده است.
2. تاریخچهٔ PWA پس از قطع شبکه و reload برنامه در دسترس است.
3. مدیریت می‌تواند PWA، API و پنل مدیریت را جدا ببیند؛ دادهٔ نصب‌شده از وضعیت میزبان خوانده می‌شود، نه از ادعای یادداشت انتشار.
4. نمایش یادداشت نسخه هیچ عملیات یا تغییر داده‌ای اجرا نمی‌کند و با سابقهٔ عملیات مدیریت مخلوط نمی‌شود.
5. پس از به‌روزرسانی پذیرفته‌شده، پیام تغییرها برای همان نسخه در همان فضای ذخیره‌سازی بیش از یک‌بار تکرار نمی‌شود؛ نصب تازه، reload همان نسخه و بازگشت به نسخهٔ قبلی آن را به‌عنوان نسخهٔ جدید معرفی نمی‌کنند.
6. رکورد تکراری یا نامعتبر انتشار را رد می‌کند. انتشار رسمی بدون یادداشت معتبر برای جزء نسخه‌دار از دروازهٔ انتشار عبور نمی‌کند.
7. نسخه‌های تاریخی فقط از شواهد تأییدشده ثبت می‌شوند؛ مورد ناقص با کمبود آشکار نمایش می‌یابد و شماره یا تغییر حدس زده نمی‌شود.
8. هیچ runtime request برای تاریخچه به GitHub، اینترنت یا API جداگانه ارسال نمی‌شود.
9. متن همهٔ یادداشت‌ها در ویرایشگر کشف می‌شود؛ تغییر به انگلیسی یا متن خالی، شناسه و قابلیت ویرایش بعدی را حفظ می‌کند و قرارداد نسخه‌ها را تغییر نمی‌دهد.

## اعتبارسنجی پیاده‌سازی

- آزمون schema و lint/validation رکوردها، ترتیب نسخه‌ها، یکتایی جزء/نسخه، انتشارهای فاقد رکورد و projectionهای PWA و مدیریت.
- آزمون واحد اعلان: فقط مسیر موفق update، یک‌بار برای هر نسخه در همان فضای ذخیره‌سازی، رد پیام، reload همان نسخه، بازگشت نسخه و storage unavailable.
- آزمون قرارداد مدیریت: تفکیک فهرست تغییرها از بسته‌های نصب و تاریخچهٔ عملیات؛ برچسب نصب‌شده فقط بر اساس پاسخ وضعیت واقعی.
- بررسی خروجی‌های PWA و مدیریت برای حضور و عدم حضور فیلدها و متن‌های هر projection، همراه کنترل hash/package.
- `npm run copy:studio:coverage`، `npm run copy:studio:test` و بررسی مرورگر ویرایشگر برای استخراج/اعمال، متن انگلیسی و خالی و انتخاب پیش‌نمایش اجرا می‌شوند. `npm run management:test`، `npm run management:build` و `npm run management:browser-check` و آزمون‌های PWA و مرورگر برای نماهای mobile/desktop و حالت offline نیز لازم‌اند.
- بررسی نهایی هیچ درخواست زمان اجرا به میزبان خارجی نداشته باشد و متن UI، حالت خالی، خطا و پیام به‌روزرسانی روی مرورگر دیده شوند.
