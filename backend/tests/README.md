# تست‌های امنیتِ بک‌اند — مرحلهٔ A + مرحلهٔ B

این مجموعه **مرزها** را می‌سنجد، نه قابلیت‌ها: خانوادهٔ الف نباید دادهٔ خانوادهٔ ب
را ببیند، عضو نباید کارِ مدیر را بکند، و نشستِ باطل نباید کار کند.

**مرحلهٔ A** (پایه): صفر تغییرِ اسکیما، صفر مهاجرت، صفر تغییرِ رفتار — فقط سنجشِ
مرزها و *ثبتِ* شکاف‌ها به‌شکلِ `xfail`.

**مرحلهٔ B** (۱۴۰۵/۰۷/۰۱): مدلِ عضویت واقعاً ساخته شد (مهاجرت `0006`)، پس سه شکافِ
#۲/#۳/#۶ **بسته** شدند و تست‌هایشان از `xfail` به **قفلِ رگرسیون** ارتقا یافتند؛ و
`test_membership_flow.py` رفتارِ تازهٔ پیوستن/تأیید/ارتقا را قفل می‌کند. سه شکافِ
#۱/#۴/#۵ (خارج از دامنهٔ B) هنوز `xfail` می‌مانند.

## اجرا

یک بار وابستگی‌ها را نصب کن (از پوشهٔ `backend/`):

```
pip install -e ".[dev]"
```

بعد، هر بار فقط همین یک دستور — از پوشهٔ `backend/`:

```
python -m pytest
```

همین. دیتابیسِ تست خودش ساخته و مهاجرت داده می‌شود.

> چرا `python -m pytest` و نه خودِ `pytest`؟ چون pip گاهی `pytest.exe` را در
> پوشه‌ای می‌گذارد که روی PATH نیست و `'pytest' is not recognized` می‌گیری.
> شکلِ `python -m pytest` این مشکل را ندارد.

## پیش‌نیاز

فقط یک پستگرسِ در دسترس. نشانی‌اش از `DATABASE_URL` (یا `.env`) خوانده می‌شود و
مجموعه **خودش** کنارش یک دیتابیسِ جدا با پسوند `_test` می‌سازد و تا `head`
مهاجرت می‌دهد. مثلاً `…/khaneyar` ← `…/khaneyar_test`.

کاربرِ دیتابیس باید اجازهٔ `CREATE DATABASE` داشته باشد. اگر نمی‌خواهی این‌طور
باشد، نشانیِ دیتابیسِ تست را دستی بده (نامش باید به `_test` ختم شود):

```
set TEST_DATABASE_URL=postgresql+psycopg://user:pass@localhost:5432/khaneyar_test
```

پستگرسِ واقعی لازم است و SQLite جایش را نمی‌گیرد: مرزِ ایزوله در خودِ دیتابیس با
RLS اجرا می‌شود و SQLite نه RLS دارد نه `set_config` — روی آن همه‌چیز «سبز» نشان
داده می‌شود بی‌آنکه چیزی سنجیده شده باشد.

## سه قفلِ ایمنی

تست‌ها پیش از هر تست جدول‌ها را `TRUNCATE` می‌کنند. برای همین اگر هر کدام از این
سه شرط برقرار نباشد، مجموعه **اصلاً شروع نمی‌شود**:

۱. نامِ دیتابیسِ تست با دیتابیسِ برنامه یکی نباشد.
۲. نامِ دیتابیسِ تست به `_test` ختم شود.
۳. `APP_ENV` روی `production` نباشد.

نشانیِ اتصال (که رمز درونش است) هیچ‌جا چاپ نمی‌شود؛ در پیام‌های خطا فقط «نامِ
دیتابیس» می‌آید. فایل‌های آپلودیِ تست هم در یک پوشهٔ موقتِ سیستمی نوشته می‌شوند،
نه در `backend/var/`.

## خروجی را چطور بخوانیم

| نشانه | معنی |
| --- | --- |
| `passed` | مرز سرِ جایش است. |
| `failed` | **مرز شکسته.** فوری. |
| `xfailed` | شکافِ *شناخته‌شده و ثبت‌شده*. انتظارش را داریم. |
| `xpassed` | شکافی **بسته شده** — از فهرستِ شکاف‌ها درش بیاور. |
| `skipped` | سنجش معنا نداشت (پایین را ببین). |

اجرای سالمِ **مرحلهٔ B** این شکل را دارد: **۹۸ `passed` + ۳ `xfailed` + صفر
`failed`**. آن ۳ تا فقط شکاف‌های باقی‌مانده‌اند (#۱ فایل، #۴ ممیزی، #۵ عدم‌تقارنِ
PATCH). این خط از خطِ پایهٔ مرحلهٔ A (۶۳ passed + ۲۵ xfailed) این‌طور آمده: با رفعِ
شکافِ #۶ آن ۱۹ آزمونِ داده‌محور دیگر مسدود نیستند و سبز می‌شوند، سه شکافِ #۲/#۳/#۶
سبز می‌شوند، و ۱۳ آزمونِ تازهٔ `test_membership_flow.py` اضافه می‌شود
(۶۳+۱۹+۳+۱۳=۹۸). مهمِ اصلی این است که **هیچ `failed` نباشد**.

**مرحلهٔ C** (۱۴۰۵/۰۷/۱۵) ۱۶ آزمونِ `test_notifications.py` را اضافه می‌کند،
**§۱.۹ قبوض** (۱۴۰۵/۰۷/۱۸) ۱۷ آزمونِ `test_bills.py` را، و **§۱.۸ خرید و انبار**
(۱۴۰۵/۰۷/۲۱) ۲۵ آزمونِ `test_shopping.py` را. در همان ۱۴۰۵/۰۷/۲۱ فهرستِ
`PROTECTED` هم از ۱۱ به ۱۷ جدول رسید (پایین را ببین) و چون دو آزمونِ
`parametrize`شده روی آن می‌چرخند، ۱۲ نمونهٔ دیگر هم اضافه شد.

> ### ✅ خطِ پایهٔ **تأییدشده** (۱۴۰۵/۰۷/۲۲ — ۲۰۲۶-۱۰-۱۴)
>
> ```
> 224 passed, 3 xfailed, 2 warnings in 107.64s
> ```
>
> نخستین اجرای کاملِ سبزِ این مجموعه. **۰ failed و ۰ skipped.** عددهای
> «مشتق‌شده از دلتا»ی قبلی (۹۸ و ۱۳۱ و ۱۶۸) همه تخمین بودند و با این اجرا
> نسخ می‌شوند — نمونه‌های `parametrize` در آن تخمین‌ها کم شمرده شده بودند.
>
> صفر بودنِ `skipped` مهم‌ترین بخشِ این خروجی است: یعنی
> `test_connection_role_is_not_exempt_from_rls` سبز شد و سنجش‌های **رفتاریِ**
> RLS واقعاً اجرا شدند. با نقشِ `postgres` همان‌ها `skip` می‌شدند و مجموعه
> «سبز» نشان می‌داد بی‌آنکه مرز سنجیده شده باشد.

### محیطِ کارکرده (ویندوز/پاورشل)

```powershell
docker ps -a --filter name=khaneyar-pg      # هست؟ → docker start khaneyar-pg
# نبود:
docker run -d --name khaneyar-pg -e POSTGRES_PASSWORD=postgres -p 5432:5432 postgres:16
docker exec -i khaneyar-pg psql -U postgres -c "CREATE ROLE apptest LOGIN PASSWORD 'test' CREATEDB;"
# بعد، در همان پنجره:
$env:TEST_DATABASE_URL = "postgresql+psycopg://apptest:test@localhost:5432/khaneyar_test"
python -m pytest
```

**پاورشل است نه cmd:** `$env:X = "..."` نه `set X=...`؛ و متغیر فقط در همان
پنجره زنده است. نقشِ `apptest` با `CREATEDB` عمدی است، نه `postgres` — دلیلش
بالا.

### اگر «N errors» دیدی (نه failed)

یعنی **دیتابیس در دسترس نیست**، نه رگرسیونِ کد. فیکسچرِ `database` در
`conftest.py` با `ConnectionTimeout` می‌افتد، پس *همهٔ* تست‌ها در setup به‌شکلِ
`error` می‌افتند و فقط `xfail`ها زنده می‌مانند (چون همان خطای setup را جذب
می‌کنند). الگوی «۲۲۴ error + ۳ xfailed» دقیقاً همین است و دو بار پیش آمده.

علت را با این ببین، نه با `short test summary info` که علت را **نشان نمی‌دهد**:

```powershell
python -m pytest -x -q --tb=short
```

> **تاریخچه:** شمارش‌های پیشینِ این فایل (۹۸ / ۱۳۱ / ۱۶۸) همه از دلتا مشتق
> شده بودند، چون VMِ توسعه پستگرس ندارد و کسی هم اجرا نگرفته بود. اجرای
> ۱۴۰۵/۰۷/۲۲ آن‌ها را با عددِ واقعی (**۲۲۴**) جایگزین کرد. درسِ عمومی‌اش این
> است: عددِ مشتق‌شده از دلتا نمونه‌های `parametrize` را کم می‌شمارد — به
> خروجیِ واقعی تکیه کن، نه به حساب‌وکتاب.

### اگر `skipped` دیدی

یعنی کاربرِ دیتابیس `superuser` است یا `BYPASSRLS` دارد. چنین نقشی **حتی با
FORCE** از RLS رد می‌شود، پس سنجشِ رفتاریِ RLS چیزی را ثابت نمی‌کند و کنار گذاشته
می‌شود. علتِ اصلی را همیشه یک تستِ قرمز اعلام می‌کند:
`test_connection_role_is_not_exempt_from_rls`. این ایرادِ *محیط* است نه کد — با
یک کاربرِ معمولی (بدون superuser) تست بگیر.

## نُه فایل

| فایل | چه چیزی را قفل می‌کند |
| --- | --- |
| `test_tenant_isolation.py` | خانوادهٔ الف ↔ خانوادهٔ ب: هیچ روتی نشت نکند. |
| `test_role_authorization.py` | عضو ≠ مدیر: بودجه، حذفِ عضو، تنظیماتِ خانواده. |
| `test_session_boundary.py` | نشست: بی‌توکن، توکنِ جعلی، خروج، خروج از همه. |
| `test_rls_database.py` | خودِ پستگرس: پالیسی‌ها روشن، FORCE شده و fail-closed. |
| `test_membership_flow.py` | **(مرحلهٔ B)** پیوستن با کد/لینک → تأیید/ردِ مدیر → گیتِ ورود؛ ارتقا/تنزل، سقفِ دو مدیر، مصونیتِ سازنده، ایزولهٔ درخواست‌ها. |
| `test_notifications.py` | **(مرحلهٔ C / §۷)** `/notifications/*`: زمینهٔ RLS، per-member بودنِ ترجیح و نادیده‌گرفتن، جزئی‌بودنِ PATCH، مهارِ ورودی. |
| `test_bills.py` | **(§۱.۹)** `/bills/*`: اتمیک‌بودنِ «پرداخت» (حالتِ قبض **و** تراکنش با هم)، ضدِ شمارشِ دوبل، قفلِ قبضِ پرداخت‌شده، مرزِ خانواده. |
| `test_shopping.py` | **(§۱.۸)** `/shopping/*` و `/inventory/*`: اتمیک‌بودنِ «خرید انجام شد» (قلم **و** تراکنش **و** موجودیِ انبار با هم)، ضدِ شمارشِ دوبل، معنیِ آستانهٔ صفر، نسبی‌بودنِ adjust، مرزِ خانواده. |
| `test_known_gaps.py` | سه شکافِ باقی‌مانده (`xfail`) + سه قفلِ رگرسیونِ #۲/#۳/#۶ (بسته‌شده در B). |

`test_rls_database.py` عمداً از اپ نمی‌پرسد و مستقیم از کاتالوگِ پستگرس می‌خواند.
دلیلش این است که تست‌های HTTP سبز می‌مانند حتی اگر RLS کلاً خاموش شود — تا وقتی
کدِ پایتون درست فیلتر می‌کند. یعنی شبکهٔ ایمنیِ دوم می‌تواند بی‌صدا بیفتد.

`test_bills.py` بیشترِ assertهایش «حالت **و** تراکنش» را با هم می‌سنجد، نه فقط
کدِ پاسخ. دلیلش این است که کدِ وضعیت به‌تنهایی گول‌زننده است: یک ۴۰۹ می‌تواند
برگردد و تراکنش هم ساخته شده باشد — و آن یعنی خرجِ ماه دو برابر شمرده شود.

`test_notifications.py` یک باگِ واقعی را همان لحظهٔ نوشته‌شدن گرفت: دو مسیرِ
`prefs` اولش `get_current_member` داشتند، با این استدلال که «ترجیحات ستونِ
`members` است و آن جدول از RLS مستثناست». استدلال درست بود ولی معیار غلط:
پاسخِ همان مسیر فهرستِ `notification_dismissals` را هم دارد و آن جدول زیرِ
RLS + FORCE است، پس بی‌زمینه **صفر ردیف** برمی‌گشت — بی هیچ خطایی. قاعده‌ای که
از این درس در آمد: **اگر درخواست حتی یک جدولِ RLSدار را بخواند، وابستگی‌اش
`get_tenant_member` است** — نه بر پایهٔ اینکه «مفهوم» کجا زندگی می‌کند.

## سه شکافِ باقی‌مانده (`xfailed`)

این‌ها تستِ *پذیرشِ* رفعِ آینده‌اند: هر assert رفتارِ **مطلوب** را می‌نویسد، پس
امروز `xfailed` است و روزِ رفع، `xpassed` می‌شود. (شماره‌ها از فهرستِ اصلیِ ممیزی
نگه داشته شدند تا ارجاع‌ها نشکنند.)

۱. **§۵.۵ فایل** — `GET /files/{path}?sig=` عمداً بی‌احراز است؛ امضا یک «قابلیتِ
   حامل» است و هر کس URL را داشته باشد بایت‌ها را می‌گیرد. عضویتِ خانواده سنجیده
   نمی‌شود.
۴. **§۲.۸ ممیزی** — هیچ جدولِ audit/activity در اسکیما نیست؛ عملیاتِ حساس ردِّ
   پایدار نمی‌گذارند.
۵. **عدم‌تقارنِ تراکنش** — `DELETE` مهارِ «فقط ردیفِ خودت» دارد ولی `PATCH` ندارد،
   پس عضوِ عادی می‌تواند تراکنشِ مدیر را ویرایش کند.

## سه شکافِ بسته‌شده در مرحلهٔ B (اکنون قفلِ رگرسیون)

این‌ها دیگر `xfail` نیستند؛ رفتارِ درست برقرار است و تست‌ها **باید سبز بمانند**.
اگر روزی قرمز شدند، یعنی رفعِ مرحلهٔ B واپس‌گرد کرده.

۲. **§۲.۶ دعوت (الف)** — پذیرشِ دعوت دیگر بی‌درنگ نشست نمی‌سازد؛ یک `join_request`ِ
   `pending` می‌سازد و تا **تأییدِ مدیر** نه ورود ممکن است نه دسترسی به داده.
۳. **§۲.۶ دعوت (ب)** — توکنِ دعوت **تک‌مصرفه** شد؛ پس از اولین پذیرش سوزانده می‌شود
   و لینکِ لو‌رفته بارِ دوم کار نمی‌کند.
۶. **زمینهٔ RLS پس از `commit`** — زمینهٔ خانواده حالا روی `Session.info` می‌نشیند
   (پایدار پس از `commit`، مستقلِ از threadpool)، پس دوباره‌خوانیِ ردیف در مسیرِ
   نوشتن دیگر صفر ردیف نمی‌بیند و ۲۰۱/۲۰۰ می‌دهد. با همین، آن ۱۹ آزمونِ داده‌محورِ
   قبلاً-مسدود هم سبز شدند و مهارِ `expect_status` (که ۵۰۰→xfail می‌کرد) از
   `conftest.py` برداشته شد — پس ۵۰۰ دوباره «شکستِ سخت» است.

> **بازمانده روی مورد ۶ (سمتِ کاربر):** رفعِ کد لازم بود ولی کافی نیست. اگر نقشِ
> اتصالِ دیتابیسِ **تولید** هنوز `superuser`/`BYPASSRLS` باشد، RLS دور زده می‌شود.
> راستی‌آزمایی: `SELECT rolsuper, rolbypassrls FROM pg_roles WHERE rolname =
> current_user;` روی اتصالِ تولید باید هر دو `false` باشد.

## وقتی جدولِ تازه‌ای می‌سازی

اگر جدولِ تازه ستونِ `family_id` داشته باشد و پالیسی نداشته باشد،
`test_every_family_id_table_is_classified` **قرمز** می‌شود — پیش از آنکه روتی
برایش نوشته شود و نشت واقعی شود. دو راه بیشتر نیست: یا برایش پالیسیِ RLS بنویس و
به `PROTECTED` اضافه‌اش کن، یا با **دلیلِ مکتوب** در `EXEMPT` ثبتش کن.

و اگر به `PROTECTED` اضافه‌اش کردی، **تابعِ `_populate` را هم به‌روز کن**: آن
تابع در هر جدولِ محافظت‌شده یک ردیف می‌سازد و همین داده است که «بدونِ زمینه صفر
ردیف» را از یک تستِ توخالی به سنجشِ واقعی تبدیل می‌کند (جدولِ خالی هم صفر ردیف
می‌دهد). بی آن، «شاهدِ مثبت» قرمز می‌شود.

> این تله یک‌بار سرِ خودمان آمد: `join_requests` (۰۰۰۶)، `bills` (۰۰۱۰) و
> `notification_dismissals` (۰۰۰۹) هر سه RLS و پالیسی داشتند ولی به `PROTECTED`
> اضافه نشده بودند. تست درست کار می‌کرد؛ فقط هیچ‌وقت اجرا نشده بود.
