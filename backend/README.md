# خانه یار — بک‌اند (FastAPI)

بک‌اند مستقل «خانه یار» که جای Supabase (Postgres + RPCها + PostgREST + Storage + توابع Vercel) را می‌گیرد.

## معماری لایه‌ای

```
app/
  core/        پیکربندی، امنیت (Argon2id + توکن)، خطاها، لاگ
  db/          اتصال SQLAlchemy + Base  (فاز ۳)
  models/      مدل‌های ORM جداول  (فاز ۳)
  schemas/     مدل‌های Pydantic ورودی/خروجی  (فاز ۶+)
  services/    منطق کسب‌وکار (قواعد سمت سرور)  (فاز ۴+)
  api/v1/      روترها و اندپوینت‌ها
  main.py      کارخانهٔ نرم‌افزار + میان‌افزار + هندلر خطا
alembic/       مهاجرت‌های نسخه‌دار دیتابیس  (فاز ۳)
tests/         تست‌ها  (فاز ۱۲)
```

## راه‌اندازی محلی

```bash
cd backend
python -m venv .venv && source .venv/bin/activate   # ویندوز: .venv\Scripts\activate
pip install -e ".[dev]"
cp .env.example .env        # سپس مقادیر واقعی را در .env بگذارید
uvicorn app.main:app --reload --port 8000
```

بررسی سلامت: `GET http://localhost:8000/healthz`
مستندات تعاملی: `http://localhost:8000/docs` (فقط در حالت توسعه)

## مهاجرت‌های دیتابیس (Alembic)

نشانی دیتابیس از `DATABASE_URL` در `.env` خوانده می‌شود (نه از `alembic.ini`).

```bash
cd backend
alembic upgrade head          # ساخت کل اسکیمای کانونی (۱۸ جدول)
alembic downgrade -1          # بازگشت یک نسخه
alembic current               # نسخهٔ فعلی دیتابیس
alembic history               # تاریخچهٔ نسخه‌ها
```

نسخهٔ اولیه `0001_initial` تمام ۱۸ جدول را از نو و تمیز می‌سازد — بدون آرتیفکت‌های
سوپابیس (RPCهای SECURITY DEFINER، گرنت‌های PostgREST). دو نکتهٔ کلیدی این نسخه:

- **رفع D-7:** قید نوع تراکنش اکنون `('expense','income','transfer')` است؛ ثبت انتقال دیگر خطا نمی‌دهد.
- **رفع D-3:** ستون `sessions.token` هش SHA-256 توکن را نگه می‌دارد، نه توکن خام.

برای ساخت نسخهٔ بعدی پس از تغییر مدل‌ها:

```bash
alembic revision --autogenerate -m "توضیح تغییر"
# فایل تولیدشده را حتماً مرور کنید (autogenerate قیدهای بی‌نام و افزونه‌ها را نمی‌بیند)
```

> پالیسی‌های RLS در مهاجرت `0002_rls` اضافه شده‌اند (بخش «RLS و مرز خانواده» پایین‌تر).
> دادهٔ فاز ۱۰ با ابزار **«فقط ضروری»** ([`migration/migrate_essentials.py`](migration/migrate_essentials.py)،
> رانبوک: [`migration/RUNBOOK.md`](migration/RUNBOOK.md)) وارد همین اسکیمای ساخته‌شده می‌شود:
> فقط families/members/accounts/دسته‌ها + جدول مرجع `card_bins`؛ تراکنش/پیامک/رویداد و
> فایل‌ها (آواتار/رسید) از صفر، و `national_id` هرگز منتقل نمی‌شود. **مهم:** چون RLS با
> `FORCE` است، `0002` باید «پس از» بار دادهٔ فاز ۱۰ اجرا شود — یعنی `upgrade 0001` → بار
> داده → `upgrade head` (ابزار خودش این ترتیب را بررسی می‌کند).

  بدون این متغیرها رفتار دقیقاً مثل قبل است (غیرمخرب).

## RLS و مرز چند-مستأجری (فاز ۵)

دفاع در عمق در سطح دیتابیس: حتی اگر لایهٔ نرم‌افزار فیلتر `family_id` را فراموش کند، خود
Postgres ردیف‌های خانواده‌های دیگر را نه می‌خواند و نه می‌نویسد.

**دامنه — ۹ جدول «همیشه‌احرازشده»** که RLS خانواده می‌گیرند (`ENABLE` + `FORCE` +
یک پالیسی `FOR ALL`): `transactions`، `transaction_photos`، `accounts`،
`subcategories`، `custom_categories`، `category_budgets`، `sms_messages`،
`sms_bridges`، `family_events`.

**بیرون از RLS و چرا:** `members`/`families`/`family_invites` لایهٔ «بوت‌استرپ
هویت»‌اند — ورود با شماره، ثبت‌نام و باز کردن لینک دعوت پیش از داشتن زمینهٔ خانواده
به آن‌ها دسترسی دارند، پس با tenancy لایهٔ نرم‌افزار محافظت می‌شوند. `sessions`،
`otp_codes`، `auth_attempts`، `lookup_attempts` (احراز، بدون family_id) و
`card_bins`/`app_settings` (سراسری) هم خانواده‌محور نیستند.

**مکانیزم:** هر درخواست احرازشده باید وابستگی `get_tenant_member` را بگیرد؛ این
وابستگی `app.family_id` (برابر family_id عضو) را روی تراکنش می‌گذارد. یک شنوندهٔ
`after_begin` در `app/db/rls.py` این مقدار را روی «هر» تراکنش آن درخواست دوباره
اعمال می‌کند (چون `commit`‌های میان‌راهی سرویس‌ها GUC transaction-local را پاک
می‌کنند). محمل پالیسی:

```sql
family_id = NULLIF(current_setting('app.family_id', true), '')::uuid
```

**fail-closed:** اگر زمینه ست نشده باشد (`get_tenant_member` به‌کار نرفته باشد)،
مقدار NULL می‌شود و `family_id = NULL` هیچ‌گاه true نیست → صفر ردیف و رد هر نوشتن.
هویت هرگز از بدنهٔ کلاینت نمی‌آید؛ `family_id` از خود عضو توکن استخراج می‌شود.

**FORCE چرا:** نرم‌افزار فعلاً با نقش مالک جدول‌ها متصل است و مالک به‌صورت پیش‌فرض از RLS
معاف است؛ `FORCE` مالک را هم مشمول می‌کند. نقش کم‌دسترسی جدا (نرم‌افزار ≠ مالک) سخت‌سازی
اختیاری فاز ۱۱ است (وابسته به هاست).

## احراز هویت (فاز ۴)

توکن نشست **فقط** از هدر `Authorization: Bearer <token>` خوانده می‌شود؛ هیچ اندپوینتی
توکن را از بدنه نمی‌پذیرد. توکن خام فقط یک‌بار هنگام ورود/ثبت‌نام برمی‌گردد و در سرور
تنها هش SHA-256 آن ذخیره می‌شود (رفع D-3).

معناشناسی نشست: `expires_at` = سقف مطلق ۹۰ روز از ساخت (تمدید نمی‌شود)،
`last_seen_at` = پنجرهٔ لغزان ۷ روزه (با هر استفاده تازه می‌شود). نشست معتبر است اگر
`now < expires_at` **و** `now < last_seen_at + ۷ روز`.

رمز عبور با Argon2id هش می‌شود؛ هش‌های قدیمی bcrypt یا `sha256(phone:password)` هنگام
ورود موفق به Argon2id ارتقا می‌یابند. حداقل طول ۸ کاراکتر فقط هنگام «تعیین» رمز اعمال
می‌شود (ثبت‌نام، پذیرش دعوت، تغییر رمز)، نه هنگام ورود.

قفل ضد brute-force متمرکز است: هر مسیر بررسی رمز/OTP از گیت مشترک `attempts` می‌گذرد
(۱۰ خطا در ۱۵ دقیقه → `TOO_MANY_ATTEMPTS`). تلاش ناموفق پیش از خطا `commit` می‌شود تا
شمارش صرف‌نظر از اندپوینت پایدار بماند.

### دو محورِ مستقلِ مهارِ نرخ

این دو را با هم اشتباه نگیرید؛ هر کدام حمله‌ای را می‌بندد که دیگری نمی‌بیند:

| | `services/attempts.py` | `services/ratelimit.py` |
| --- | --- | --- |
| کلیدِ سطل | **شمارهٔ موبایل** | **مبدأ درخواست** (IP) |
| جدول | `auth_attempts` | `lookup_attempts` (ستونِ `scope`) |
| پنجره | ۱۵ دقیقه، ۱۰ خطا | `RL_WINDOW_SECONDS` (پیش‌فرض ۶۰ ثانیه) |
| می‌شمارد | فقط تلاشِ **ناموفق** | **هر** درخواست (موفق یا ناموفق) |
| حمله‌ای که می‌بندد | حدسِ رمزِ یک حساب | credential stuffing، شمارشِ کد/شماره، سیلِ ثبت‌نام |

سطلِ per-IP لازم بود چون شمارندهٔ اول با «شماره» کلید می‌خورد: مهاجمی که یک رمزِ
رایج را روی هزار شمارهٔ **مختلف** می‌آزماید هیچ‌گاه به قفلِ ۱۵دقیقه‌ای نمی‌خورد.
به‌همین‌شکل `POST /auth/join` (کدِ ۶رقمیِ خانواده، فضای جست‌وجو فقط یک‌میلیون)
هیچ گیتی نداشت.

**حریمِ خصوصی:** نشانیِ خامِ IP هیچ‌جا ذخیره نمی‌شود. ستونِ `scope` مقدارِ
HMAC-SHA256ِ نمک‌خورده (۳۲ هگز = ۱۲۸ بیت) است، تا این جدول به گزارشِ «چه کسی از
کجا چه شماره‌ای را پرسید» بدل نشود (§۵). نمک از `RATE_LIMIT_SALT` می‌آید و اگر
خالی باشد از `FILE_SIGNING_SECRET`؛ اگر هر دو خالی باشند نمکِ تصادفیِ
درون‌فرایندی ساخته می‌شود که با هر ری‌استارت شمارنده را صفر می‌کند (و هشدار لاگ
می‌شود) — پس در تولید یکی از این دو را ست کنید.

**نشانیِ کلاینت** با `app/core/netaddr.py` استخراج می‌شود. تنها هدرِ مرجع
`X-Real-IP` است (چون nginx آن را با `$remote_addr` **بازنویسی** می‌کند) و فقط
وقتی خوانده می‌شود که خودِ peer در فهرستِ صریحِ شبکه‌های داخلی باشد.
`X-Forwarded-For` عمداً نادیده گرفته می‌شود چون nginx به آن **اضافه** می‌کند و
بخشِ سمتِ چپش را کلاینت می‌نویسد. اگر نشانی‌ای پیدا نشد، رشتهٔ `"unknown"`
برمی‌گردد — یعنی همهٔ چنین درخواست‌هایی در یک سطل می‌افتند (fail-closed، سخت‌گیرتر
نه بازتر).

> ⚠️ از `addr.is_private` برای تشخیصِ «peerِ داخلی» استفاده **نکنید**:
> `ip_address("203.0.113.9").is_private` در پایتون True است (بازه‌های مستندسازیِ
> RFC 5737 را هم «خصوصی» می‌شمارد)، و نتیجه‌اش اعتماد به هدرِ جعلی است. فهرستِ
> صریحِ `_LOCAL_NETWORKS` جای آن است و تستِ
> `test_documentation_ranges_are_not_trusted_as_local_peers` قفلش می‌کند.

سقفِ صفر = بی‌سقف. کلیدها: `RL_LOGIN_PER_IP`، `RL_CHECK_PASSWORD_PER_IP`،
`RL_PRE_REGISTERED_PER_IP`، `RL_JOIN_PER_IP`، `RL_REGISTER_PER_IP`،
`RL_OTP_REQUEST_PER_IP`، `RL_PASSWORD_RESET_PER_IP` (نمونه در `.env.example`).
در تست‌ها همهٔ این سقف‌ها خاموش‌اند و فیکسچرِ `rate_limit` آن‌ها را برای تستِ
مربوطه روشن می‌کند — دلیلش در `tests/conftest.py` نوشته شده.

### درگاهِ پیامکِ خروجی

`services/sms.py` تنها راهِ تحویلِ کدِ یک‌بارمصرف است (پیش از این بک‌اند هیچ
فرستندهٔ پیامکی نداشت؛ `services/messaging.py` سراسر **ورودی** است). یک درزِ
باریک با دو پیاده‌سازی:

| کلید `.env` | معنا |
| --- | --- |
| `SMS_PROVIDER` | فعلاً تنها درگاهِ شناخته‌شده `kavenegar` است. **خالی هم یعنی همان** (پیش‌فرضِ `config.py` خالی است)؛ مقدارِ ناشناس → خنثی + خطای لاگ |
| `SMS_API_KEY` | **تا وقتی خالی است هیچ پیامکی ارسال نمی‌شود** |
| `SMS_TEMPLATE` | نامِ قالبِ `verify/lookup` در پنل. پرش کنید تا متنِ آزاد برود |
| `SMS_SENDER` | خطِ فرستنده — فقط برای مسیرِ متنِ آزاد |
| `SMS_TIMEOUT_SECONDS` | مهلتِ HTTPِ درگاه |

**قاعدهٔ خنثی‌بودن:** بی‌کلید، `get_sender()` یک `NullSmsSender` می‌دهد که چیزی
نمی‌فرستد و **هرگز خطا بالا نمی‌برد** — پس مخزن بی‌هیچ کلیدی قابلِ اجرا و تست
است و روشن‌شدنِ تولید *تنها* با پرکردنِ `.env` رخ می‌دهد. در توسعه کد را در لاگ
می‌گذارد تا کار جلو برود؛ در تولید **نه** (§۵ — دادهٔ حساس در لاگ نه).

قالبِ `verify/lookup.json` بر متنِ آزاد ترجیح دارد: پیامکِ «خدماتی» است، پس
فیلتر نمی‌شود و خطِ اختصاصی نمی‌خواهد.

> ⚠️ کاوه‌نگار کلید را **در مسیرِ URL** می‌گیرد
> (`/v1/{API-KEY}/verify/lookup.json`)، نه در کوئری. پس فیلترِ `?key=…` در
> `app/core/logging.py` این شکل را نمی‌گرفت و `httpx.HTTPStatusError` آدرسِ کامل
> را داخلِ پیامِ خودش می‌گذارد. دو مهار گذاشته شد: الگوی مسیرِ کاوه‌نگار به همان
> فیلتر اضافه شد، و هر متنِ خطا پیش از مصرف از `_scrub` رد می‌شود. اگر روزی
> درگاهِ دیگری اضافه شد، همین دو نقطه را وارسی کنید.

`deliver_code()` نقطهٔ ورودِ امن است و **هرگز** خطا بالا نمی‌برد: خطای ارسال
`SmsDeliveryError` (نه `AppError`) است و به کلاینت راه ندارد، چون در مسیرِ
بازیابیِ رمز پاسخ باید برای شمارهٔ ثبت‌شده و ثبت‌نشده یکسان بماند.

### بازیابیِ رمزِ فراموش‌شده (§۹.۵)

دو گام، و همهٔ طراحی حولِ یک چیز است: **هیچ‌کس نباید بتواند از این مسیر بفهمد
یک شماره ثبت شده است یا نه.**

`POST /auth/password-reset/request` **همیشه** `{"ok": true}` می‌دهد — شمارهٔ
ناشناس، شمارهٔ در کول‌داون، و شمارهٔ واقعی همه یک پاسخ می‌گیرند. سه پیامدِ
عمدی: (۱) کول‌داونِ ۶۰ثانیه‌ای **بی‌صداست** (اگر `TOO_SOON` می‌داد، خودش
اوراکلِ شمارشِ حساب می‌شد)، (۲) ارسالِ پیامک در `BackgroundTasks` می‌رود تا
زمانِ پاسخ هم نشتی نداشته باشد، (۳) کد **هرگز** در بدنهٔ پاسخ برنمی‌گردد — حتی
در حالتِ توسعه، که در آن کد به لاگِ سرور می‌رود.

`POST /auth/password-reset/confirm` کد را **بی‌قید‌و‌شرط** می‌سنجد (مستقل از
پرچمِ `otp_enabled`؛ `verify_and_consume` نه `consume_otp`)، رمز را با Argon2id
می‌نشاند و بعد `logout_all` می‌زند — **همهٔ** نشست‌ها، نه `revoke_others` که
`change-password` می‌زند: فرضِ بازیابی این است که رمزِ قبلی از دستِ کاربر خارج
شده. پاسخ نشست نمی‌دهد؛ کاربر از مسیرِ عادیِ ورود می‌آید تا گیتِ وضعیتِ عضویت
(§۲.۶) هم اعمال شود. ترتیبِ درونی عمدی است: سقفِ نرخ → طولِ رمز → مصرفِ کد، تا
یک رمزِ کوتاه کدِ درستِ کاربر را نسوزاند.

کدها در `otp_codes` با `purpose` (`login` / `password_reset`) و **هش‌شده**
(`code_hash`، HMAC-SHA256ِ فلفل‌خورده) می‌نشینند — مهاجرتِ `0008`. بی‌`purpose`
کدی که برای ورود فرستاده شده بود می‌توانست رمز را عوض کند. فلفل از
`RATE_LIMIT_SALT` می‌آید، بعد `FILE_SIGNING_SECRET`؛ اگر هر دو خالی باشند
درون‌فرایندی می‌شود و کدهای در جریان با هر ری‌استارت می‌میرند (هشدارِ لاگ).

> ⚠️ همان حالتِ «فلفلِ درون‌فرایندی» سرور را به **تک‌ورکر** بودن گره می‌زند: با
> `uvicorn --workers N` کدی که ورکرِ A هش کرده در ورکرِ B رد می‌شود، و در سقفِ
> نرخ هم چون `scope` همان HMAC است، یک IP در هر ورکر کلیدِ جدا می‌گیرد و سقف
> عملاً در N ضرب می‌شود. `backend/Dockerfile` فعلاً تک‌ورکر است و یادداشتِ هشدار
> کنارِ `CMD` هست. راهِ درستِ هر دو یکی است: `RATE_LIMIT_SALT` را در `.env`ِ
> تولید بگذار.

`GET /auth/config` پرچمِ `password_reset_enabled` را می‌دهد که از تکیه‌گاهِ تکِ
`password_reset.is_available()` می‌آید: «کلیدِ پیامک هست، یا اینجا تولید نیست».
عمداً وضعیتِ **سرور** است نه چیزی دربارهٔ کاربر — وگرنه خودِ همین پرچم می‌شد
اوراکلِ شمارش. روی تولیدِ بی‌کلید مسیر خودش را خاموش اعلام می‌کند
(`SMS_NOT_CONFIGURED/503`) و کلاینت دکمهٔ «فراموشیِ رمز» را نشان نمی‌دهد.

تست‌ها در `tests/test_password_reset.py` (۲۲ تست). چون کد نه در پاسخ می‌آید و نه
خام ذخیره می‌شود، تنها نقطهٔ گرفتنش درزِ ارسال است: فیکسچرِ `outbox` تابعِ
`sms.deliver_code` را با یک ضبط‌کننده جا‌به‌جا می‌کند.

### سخت‌سازیِ ۲۰۲۶-۰۹-۲۸ — چهار چیزی که «ساده» نیستند

اینها از یک ممیزیِ مستقل روی همان کدِ بالا درآمدند. هر کدام کوتاه به‌نظر می‌رسد
و هر کدام اگر ساده شود، کارِ §۹.۵ را بی‌اثر می‌کند.

**۱) `burn_verify_cost()` را از `check_password_gated` برندار.** Argon2id حدودِ
۱۰۰ms می‌برد و پیش از این فقط برای عضوِ *موجود* اجرا می‌شد؛ یعنی زمانِ پاسخِ
`/auth/check-password` و `/auth/login` می‌گفت کدام شماره ثبت شده. آن‌وقت کلِ کارِ
ضدِ‌شمارشِ بالا بی‌فایده بود، چون مهاجم سراغِ این اندپوینت می‌رفت نه مسیرِ
بازیابی. حالا شاخهٔ «عضو نیست» هم همان هزینه را می‌سوزاند. **پیامدِ عمدی:**
ورودِ ناموفق با شمارهٔ ناشناس ~۱۰۰ms کندتر است — این بهاست، نه کندی.

**۲) گاردِ بازیابی `member is None or not member.password_hash` است، نه فقط
`member is None`.** عضوی که *مدیر* ساخته `status='pending'` دارد ولی
`membership_state` پیش‌فرضِ `'active'`، و `_ensure_can_login` تنها دومی را
می‌سنجد. بی‌این گارد، هرکس شمارهٔ چنین عضوی را می‌دانست می‌توانست با «فراموشیِ
رمز» رمز بگذارد و بی‌گذشتن از `/auth/register` وارد شود.

**۳) `is_configured()` هم کلید را می‌سنجد هم شناخته‌بودنِ درگاه.** با فقط
سنجشِ کلید، یک `SMS_PROVIDER`ِ غلط‌نوشته «آری» می‌گرفت در حالی که `get_sender()`
فرستندهٔ خنثی می‌داد: کد ساخته می‌شد، کاربر «۲۰۰ خالی» می‌گرفت و هیچ پیامکی
نمی‌رفت. `provider_name()` مقدارِ خالی یا فقط‌فاصله را `kavenegar` می‌خواند
(پیش‌فرضِ `config.py` خالی است)؛ درگاهِ ناشناس خطا لاگ می‌کند و خنثی برمی‌گردد.

**۴) مصرفِ کد با `UPDATE … WHERE used = false` است، نه `row.used = True`.** زیرِ
READ COMMITTED دو درخواستِ هم‌زمان با یک کد هر دو از `SELECT` رد می‌شدند و هر دو
موفق می‌گشتند — یعنی **دو رمزِ متفاوت با یک کد**. حالا تنها یکی
`rowcount == 1` می‌گیرد و بازنده همان `INVALID_OTP` را می‌بیند.

**ماندهٔ شناخته‌شده:** در گامِ ۱، شاخهٔ شمارهٔ ثبت‌شده یک `INSERT` + `commit`
دارد که شاخهٔ ناشناس ندارد، پس دلتای ~۱–۵ms باقی است. با سقفِ ۵ درخواست‌در‌دقیقه
per-IP نمونه‌برداریِ آماری از آن بسیار پرهزینه است؛ ولی اگر روزی آن سقف برداشته
شد، اینجا را نگاه کن.

**لاگ:** ردکشن حالا در `RedactingFormatter` است نه فقط `RedactingFilter` — چون
`logging.Formatter` تراس را از `exc_info` می‌سازد و **پس از** فیلترها می‌چسباند،
پس تا پیش از این هر `log.exception` یک تراسِ نشویده بیرون می‌داد (تراسِ `httpx`
با کلیدِ کاوه‌نگار در *مسیرِ* URL، و بندِ `[parameters: …]`ِ پستگرس با
`password_hash`/`code_hash`). تست‌ها در `tests/test_log_redaction.py`.

## اندپوینت‌های نوشتن (فاز ۷)

افزودن/ویرایش/حذف زیر `/api/v1`. قرارداد REST: `POST`=ساخت، `PATCH`=ویرایش جزئی/تنظیم،
`DELETE`=حذف؛ کنش‌های خاص (مثل رسیدگی به سررسید یا هم‌گام‌سازی تولد) `POST`اند. پاسخ‌ها
با نوع بازگشت RPCهای قدیمی یکی‌اند: ردیف→`*Out` (۲۰۰/۲۰۱)، void→۲۰۴، اسکالر→`int`/`str` خام.

**اعتبارسنجی دولایه (اصل کلیدی):** بدنه‌های ورودی عمداً «سهل‌گیر»‌اند (فیلدها `Optional`
با پیش‌فرض `None`)؛ **همهٔ** قواعد کسب‌وکار در لایهٔ سرویس با `AppError` و کدهای خطای
پایدار اعمال می‌شوند. اگر اعتبارسنجی سخت را در Pydantic می‌گذاشتیم، خطاها ۴۲۲ خام
می‌شدند و نگاشت خطای کلاینت (`RPC_ERROR_MAP`) می‌شکست.

روت‌های داده (تحت `get_tenant_member` و RLS):

| متد و مسیر                                                             | معادل RPC قدیمی                                   |

| `POST /transactions/{id}/occurrences`                                  | mark_recurring_occurrence                         |

| `POST /accounts` · `PATCH/DELETE /accounts/{id}`                       | add/update/delete_account                         |
| `POST/DELETE /subcategories[/{id}]`                                    | add/delete_subcategory                            |
| `POST/DELETE /custom-categories[/{id}]`                                | add/delete_custom_category                        |
| `POST /category-budgets` · `DELETE /category-budgets/{category}`       | set/delete_category_budget (فقط مدیر)             |

> **چرا members بیرون از RLS است:** روی جدول‌های هویتی `families`/`members` کار می‌کند
> که از RLS مستثنا هستند (بخش فاز ۵)؛ پس مرز مستأجر را «لایهٔ نرم‌افزار» می‌گذارد — هر نوشتن یا
> به خود actor محدود است یا `family_id` عضو هدف صریحاً با actor سنجیده می‌شود.

**دو یافتهٔ فاز ۷ که در فاز ۹ اعمال شد (اتصال فرانت):**

1. **قالب سیم خطا:** بک‌اند `{"error": <code>, "message": <پیام فارسی>}` می‌فرستد. seam
   قدیمی ابتدا `message` را می‌خواند و رجکس‌های خطا را روی آن می‌سنجید (کدها انگلیسی،
   پیام فارسی → عدم تطبیق، سقوط به `SERVER`). در فاز ۹ `mapError` `RestClient` **کد
   `error` را مقدم بر `message`** می‌خواند (به‌ویژه `SESSION_EXPIRED` که ورود دوباره را
   راه می‌اندازد).
2. **کدهای تازه:** `INVALID_STATUS` (پیامک)، `INVALID_EVENT` (رویداد)،
   `INVALID_THEME`/`INVALID_CURRENCY` (پروفایل) و `INVALID_NAME` به `REST_ERROR_MAP`
   افزوده شدند. (`INVALID_TYPE/AMOUNT/CATEGORY/DATE/MEMBER/RELATION`،
   `EMPTY_RELATION`، `OWNER_RELATION_FIXED`، `CATEGORY_IN_USE`، `EVENT_DUPLICATE`،
   `PHONE_EXISTS`، `CANNOT_REMOVE_OWNER`، `NOT_FOUND`، `FORBIDDEN` از پیش نگاشت داشتند.)

راستی‌آزمایی ایستا: `outputs/verify_phase7.py` پوشش RPC، مرز وابستگی و گارد مدیر را
بررسی می‌کند (بدون دیتابیس/شبکه).

## پیامک و فایل سمت‌سرور (فاز ۸)

فاز ۸ دو قابلیت باقی‌ماندهٔ سوپابیس را جایگزین می‌کند: خواندن پیامک بانکی و استوریج
فایل (آواتار/رسید تراکنش). هیچ اندپوینتی هویت را از بدنه نمی‌گیرد، جز پل
ماشین‌به‌ماشین که عمداً با «توکن پل» احراز می‌شود.

### ingest پیامک

| متد و مسیر                | احراز                             | نکته                                                                             |
| ------------------------- | --------------------------------- | -------------------------------------------------------------------------------- |
| `POST /sms/ingest`        | نشست (`get_tenant_member`، RLS)   | ثبت دسته‌ای متن خام پیامک از نرم‌افزار خود کاربر؛ سرور پارس و «در انتظار» می‌کند |
| `POST /sms/bridge-ingest` | **توکن پل در بدنه** (بدون Bearer) | وب‌هوک فورواردر؛ تنها روت بی‌نشست سامانه                                         |

`bridge-ingest` تنها استثنای «هویت فقط از Bearer» است: فورواردر پیامک نمی‌تواند هدر
نشست بفرستد، پس با توکن پل (`sms_bridges`) احراز می‌شود. آن جدول در مهاجرت `0003`
عمداً از RLS خارج شد تا جست‌وجوی توکن پیش از داشتن زمینهٔ خانواده ممکن باشد؛ سپس سرویس
دستی `app.family_id` را ست و در `finally` ریست می‌کند. توکن نبود/نامعتبر →
`UNAUTHORIZED` (fail-closed). این فایل (`webhooks.py`) از روت‌های داده جداست تا مرز فاز ۷ نشکند.

### آپلود و سرو فایل

| متد و مسیر             | احراز                               | نکته                                  |
| ---------------------- | ----------------------------------- | ------------------------------------- |
| `POST /uploads/avatar` | Bearer (`get_current_member`)       | آواتار عضو؛ خارج از RLS چون هویتی است |
| `POST /uploads/photo`  | Bearer (`get_current_member`)       | رسید تراکنش؛ نام فایلْ یکتا           |
| `GET /files/{path}`    | **بدون احراز — مجوز در امضای HMAC** | سرو فایل خصوصی؛ کش ۱ ساله             |

فایل‌ها به‌صورت data-URL در بدنه می‌آیند، روی دیسک خصوصی ذخیره می‌شوند و با یک **URL
ظرفیتی امضاشده با HMAC** (پارامتر `sig`) سرو می‌شوند — نه Bearer، چون تگ `<img>`
نمی‌تواند هدر بفرستد. امضا بی‌انقضاست ولی به همان مسیر گره خورده؛ امضای نبود/نادرست →
`FORBIDDEN` (fail-closed).

متغیرهای محیطی تازهٔ فاز ۸ (نام‌ها؛ مقدار فقط در `.env`):

| متغیر                 | نقش                                                                     |
| --------------------- | ----------------------------------------------------------------------- |
| `FILE_SIGNING_SECRET` | کلید HMAC URL ظرفیتی. **اگر ست نشود، آپلود و سرو هر دو بسته می‌مانند.** |
| `STORAGE_DIR`         | ریشهٔ دیسک فایل‌های خصوصی                                               |
| `FILES_BASE_URL`      | پیشوند URL عمومی سرو فایل (برای ساخت لینک امضاشده)                      |
| `UPLOAD_MAX_BYTES`    | سقف حجم هر آپلود                                                        |

(`STORAGE_BUCKET_AVATARS`/`STORAGE_BUCKET_PHOTOS` و کلیدهای `STORAGE_ENDPOINT/ACCESS_KEY/SECRET_KEY`
برای مسیر آبجکت‌استوریج اختیاری فاز ۱۱ رزرو شده‌اند.)

### خواندن نیتیو پیامک روی اندروید

نرم‌افزار اندروید (بازار) پیامک بانکی را با پلاگین Capacitor مستقیم می‌خواند و از مسیر
`ingestRawSms` به مخزن می‌فرستد؛ وب/iOS بی‌صدا رد می‌شود و پل فورواردر فالبک است.

- پلاگین به **Java** نوشته شده (نه Kotlin): پروژهٔ اندروید افزونهٔ gradle Kotlin ندارد،
  پس Java صفر-اصطکاک بیلد و هم‌خوان با `MainActivity.java` است.
- نسخهٔ ۱ فقط **پیش‌زمینه/گرم** می‌خواند (BroadcastReceiver زمان اجرا)؛ خواندن
  پس‌زمینه به receiver مانیفست نیاز دارد (مسیر آینده). فالبک وب/iOS = ثبت دستی + پل.
- مجوز `RECEIVE_SMS`/`READ_SMS` یک‌بار پرسیده می‌شود؛ رد کاربر = صرف نظر بی‌صدا.
- **بیلد و تست APK با کاربر است.**

راستی‌آزمایی ایستا: `outputs/verify_phase8.py` سیم‌کشی روتر، مرز نشست‌در‌برابر‌پل،
دست‌نخوردگی مرز فاز ۷، امضای HMAC و fail-closed پل را بررسی می‌کند (بدون دیتابیس/شبکه).

## اتصال فرانت (فاز ۹)

سوییچ کامل و تمیز: کل فرانت از سوپابیس جدا و به همین بک‌اند وصل شد — بدون حالت دومسیرهٔ
هم‌زمان. یک `RestClient` واحد (`src/infrastructure/api/restClient.ts`) تنها seam شبکه است
و مبدأ از یک متغیر واحد `VITE_API_URL` می‌آید (`src/shared/config/apiUrl.ts`؛ پیشوند
`/api/v1`). توکن با `Authorization: Bearer` از `SessionRepository` (نقش `TokenProvider`)
به‌صورت خودکار افزوده می‌شود؛ تنها استثنا وب‌هوک `bridge-ingest` است که توکن در بدنه دارد.

- **۱۰ مخزن** بازسیم‌کشی شدند (auth، family، transactions، sms، accounts، bridges،
  subcategories، customCategories، events، categoryBudgets) — همه بدنه‌ها snake_case،
  و پارامترهای مسیر فارسی (مثل `category` در حذف بودجه) با `encodeURIComponent`.
- **ingest سمت‌سرور:** `IngestRawSmsUseCase` دیگر متن را در کلاینت پارس نمی‌کند؛ خام پیامک
  را به `POST /sms/ingest` می‌فرستد و سرور پارس/ذخیره می‌کند. مسیر چسباندن دستی
  (`parseSmsImport` + `addSmsBatch`) دست‌نخورده ماند.
- **نگاشت خطا کدـمحور شد** و کدهای تازه افزوده شدند (بخش «دو یافتهٔ فاز ۷» بالا).
- **بازنشسته (حذف نشد، طبق قاعدهٔ پروژه):** `infrastructure/api/httpClient.ts` (seam
  دومسیرهٔ `rpc`)، `shared/config/apiBase.ts` (`API_BASE`)، `shared/config/supabase.ts`
  (`supabaseConfig`) — هر سه به یادداشت فارسی + `export {}` تقلیل یافتند؛ بدنهٔ قدیمی در
  تاریخچهٔ گیت می‌ماند. هیچ کد زنده‌ای دیگر آن‌ها را import نمی‌کند.
- **ورود اجباری دوباره در لحظهٔ سوییچ خودکار است:** توکن قدیمی سوپابیس →
  `UNAUTHORIZED` از بک‌اند → نگاشت به `SESSION_EXPIRED` → پاک‌شدن نشست → صفحهٔ ورود.

> **پیش‌نیاز کارکرد:** این فاز فقط «کد» فرانت را سوییچ می‌کند. تا بک‌اند دپلوی و
> دادهٔ کاربران در فاز ۱۰ وارد نشود، نرم‌افزار روی این بک‌اند دادهٔ واقعی نشان نمی‌دهد.
> `VITE_SUPABASE_*` هنوز باید از محیط حذف و کلیدها چرخانده شوند (فاز ۱ — سمت کاربر).
