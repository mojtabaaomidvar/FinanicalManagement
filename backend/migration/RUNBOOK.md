# رانبوکِ فاز ۱۰ — مهاجرتِ داده (فقط ضروری)

راهنمای گام‌به‌گام برای انتقالِ دادهٔ اپ از **سوپابیس** به **بک‌اندِ اختصاصی (Postgres)**.
این کار را **خودتان** روی سروری که به هر دو دیتابیس دسترسی دارد اجرا می‌کنید (من دیتابیس/شبکه ندارم).

> ابزار: [`migrate_essentials.py`](migrate_essentials.py) — کنارِ همین فایل.

---

## چه چیزی منتقل می‌شود؟

**منتقل می‌شود (فقط ضروری):** خانواده‌ها، اعضا، حساب‌ها/کارت‌ها، دسته‌های سفارشی،
زیردسته‌ها، و سقفِ بودجهٔ دسته‌ها.

**از صفر شروع می‌شود (منتقل نمی‌شود):** تراکنش‌ها، عکسِ رسیدها، پیامک‌ها، پل‌های پیامک،
رویدادها، و نشست‌های ورود. **فایل‌ها هم از صفر:** آواتار و عکسِ رسیدهای قدیمی منتقل
نمی‌شوند و لینک‌های استوریجِ سوپابیس رها می‌شوند.

**دادهٔ مرجع:** جدولِ `card_bins` (نگاشتِ BIN → نامِ بانک؛ دادهٔ کاربر نیست) به‌صورتِ
پیش‌فرض منتقل می‌شود تا شماره‌کارت‌ها در اپ نامِ بانک را نشان دهند. اگر نمی‌خواهید،
`--skip-reference` را اضافه کنید.

سه قانونِ ثابت که ابزار خودکار رعایت می‌کند:

- **کدملی (national_id) هرگز منتقل نمی‌شود** — از کل برنامه حذف شده است.
- **آواتارِ اعضا اجباراً خالی (NULL) می‌شود** — چون فایل‌ها از صفرند.
- **هشِ رمزِ عبور حفظ می‌شود** — پس اعضا با **همان رمزِ قبلی** وارد می‌شوند (بک‌اندِ جدید
  هش‌های قدیمی را هنگامِ اولین ورودِ موفق به Argon2id ارتقا می‌دهد). فقط یک‌بار ورودِ
  دوبارهٔ اجباری لازم است (توکنِ قدیمیِ سوپابیس دیگر معتبر نیست).

---

## پیش‌نیازها

۱. Postgresِ مقصد بالا و در دسترس باشد (فاز ۱۱ — هاست).
۲. venv بک‌اند فعال باشد تا `psycopg` و `alembic` در دسترس باشند:

```bash
cd backend
source .venv/bin/activate      # ویندوز: .venv\Scripts\activate
pip install -e ".[dev]"        # اگر قبلاً نصب نشده
```

۳. نشانیِ هر دو دیتابیس را در متغیرِ محیطی بگذارید (در `.env` نگذارید تا در تاریخچه نماند):

```bash
export SOURCE_DATABASE_URL='postgresql://…رشتهٔ اتصالِ سوپابیس…'
export TARGET_DATABASE_URL='postgresql://…رشتهٔ اتصالِ Postgresِ جدید…'
```

> اگر `TARGET_DATABASE_URL` را ست نکنید، از همان `DATABASE_URL`ِ بک‌اند خوانده می‌شود.

## ترتیبِ حیاتی (به‌خاطرِ RLS)

جدول‌های `accounts` / `subcategories` / `custom_categories` / `category_budgets` در
مهاجرتِ **`0002`** با **FORCE RLS** بسته می‌شوند؛ آن‌گاه حتی مالکِ جدول هم بدونِ زمینهٔ
خانواده نمی‌تواند در آن‌ها بنویسد. پس داده باید **پیش از `0002`** بار شود:

```
alembic upgrade 0001   →   بارِ دادهٔ ضروری   →   alembic upgrade head
```

ابزار خودش این را می‌سنجد: اگر RLS از قبل روی مقصد فعال باشد، با پیامِ راهنما متوقف می‌شود.

## گام‌ها

### ۱) ساختِ اسکیمای پایه (بدونِ RLS)

```bash
cd backend
alembic upgrade 0001
```

این فقط ساختارِ جدول‌ها را می‌سازد؛ RLS هنوز فعال نیست.

### ۲) پیش‌نمایش (بدونِ نوشتن)

```bash
python migration/migrate_essentials.py --dry-run
```

خروجی، برای هر جدول: تعدادِ ردیفِ سورس، تعدادِ ستون‌های حمل‌شونده، ستون‌های کنارگذاشته
(`national_id`)، و ستون‌هایی که NULL می‌شوند (`avatar_url`). بررسی کنید معقول باشد.

### ۳) اجرای واقعی

```bash
python migration/migrate_essentials.py
```

کلِ بار در **یک تراکنش** انجام می‌شود؛ اگر خطایی رخ دهد، همه‌چیز برمی‌گردد و هیچ ردیفِ
نیمه‌کاره‌ای نمی‌ماند. در پایان، جدولِ راستی‌آزماییِ «سورس در برابرِ تارگت» چاپ می‌شود.

> اجرای دوباره امن است: درجِ تکراری با `ON CONFLICT (id) DO NOTHING` نادیده گرفته می‌شود.
> برای شروعِ کاملاً تمیز، `--truncate` را اضافه کنید (جدول‌های ضروریِ مقصد را خالی می‌کند).

### ۴) فعال‌سازیِ RLS و بقیهٔ اسکیما

```bash
alembic upgrade head
```

این `0002` (RLS) و `0003` را اعمال می‌کند. از این پس مرزِ خانواده در سطحِ دیتابیس فعال است.

### ۵) راستی‌آزماییِ نهایی

- خروجیِ گامِ ۳ را ببینید: تعدادِ ردیفِ تارگت باید با سورس بخواند (✓).
- یک ورودِ آزمایشی با یک عضو انجام دهید (همان شماره و رمزِ قبلی).
- چند حساب/کارت و دسته‌ها را در اپ ببینید. تراکنش‌ها طبیعتاً خالی‌اند (از صفر).

---

## پس از مهاجرت

- **ورودِ دوبارهٔ همه اجباری است** (یک‌بار)؛ رمزها همان‌اند.
- `VITE_API_URL` باید به دامنهٔ بک‌اندِ جدید اشاره کند و اپ دوباره بیلد/دپلوی شود.
- کلیدهای قدیمیِ سوپابیس را از محیط حذف و بچرخانید (**فاز ۱**).
